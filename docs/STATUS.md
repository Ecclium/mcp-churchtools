- Für das Threat Model v0 vorgemerkt:
  - Die eingebaute globale Allowlist von gitleaks gilt auch für die eigenen Regeln. Sie überspringt unter anderem Bilder einschliesslich SVG, Schriften, `pnpm-lock.yaml`, `package-lock.json`, `node_modules/` und `.gitleaks.toml` selbst. Ausserdem verwirft sie Funde, deren Wert wie ein Systempfad aussieht. Die Regel für Home-Pfade meldet deshalb nur den Benutzernamen.
  - Der von lefthook erzeugte Hook lässt einen Commit ohne Prüfung durch, wenn das Programm lefthook nicht gefunden wird. Der Hook ist deshalb nur eine erste Sicherung. CI prüft jeden Pull Request noch einmal.
  - TypeScript, `@types/node`, ESLint, `@eslint/js` und Prettier erscheinen auf npm ohne Herkunftsnachweis (Provenance), anders als Vitest, Vite, typescript-eslint, eslint-plugin-jsdoc und pnpm. Die Vertrauensrichtlinie von pnpm (`trustPolicy`) schützt diese Pakete deshalb nicht, es bleibt das Mindestalter von drei Tagen. Sie werden nie automatisch übernommen (ADR 0021).
  - Die Proben des Spikes vertrauen dem OpenAPI-Dokument der Instanz: Seine Werte stehen nicht auf der Sperrliste, seine Schlüssel dürfen in der Ausgabe erscheinen. Eigene Namen einer Instanz im Dokument fängt nur die Durchsicht vor dem Weitergeben.
  - In `02-permissions` erscheinen Namen von Rechten, wenn sie aus kleingeschriebenen Wörtern bestehen. Verrät ein solcher Name etwas über die Gemeinde und kommt er in keiner Antwort als Wert vor, fängt ihn ebenfalls nur die Durchsicht.
  - Die ESLint-Regeln zur Ausgabe sehen Code, nicht das Verhalten zur Laufzeit. Schreiben über einen berechneten Dateideskriptor, einen zusammengesetzten Pfad zu einer Gerätedatei, einen übergebenen Strom oder im Code einer Abhängigkeit erkennen sie nicht. Ab Phase 1 prüft ein Test im Betrieb über stdio die Ausgabe (ADR 0018).
  - Den rohen ChurchTools-Client schützen Regeln über direkte Importe und ein Test der Exportfläche von `core`. Ein erlaubtes Modul, das den Client als Wert weitergibt, fällt nur im Review auf (ADR 0024).
  - Das `package.json` im Wurzelordner macht alle Pakete und die Werkzeuge der Entwicklung von überall im Workspace auflösbar. Die Grenzen halten dependency-cruiser und der Test des Workspace-Graphen, nicht pnpm (ADR 0022).
  - Die Prüfungen eines Pull Requests laufen mit dessen eigenem Code. Wer ein Prüfskript oder einen Workflow ändert, kann die eigene Prüfung grün machen. Bei Pull Requests aus Forks schützen die Freigabe des Laufs und die Checkliste in `CONTRIBUTING.md` (ADR 0021).
  - Die Action, die mise installiert, legt das Token des Jobs für alle folgenden Schritte ab, auch für Tests und Install-Skripte. Jobs mit mise haben deshalb nur Leserechte. mise übernimmt ausserdem Umgebungsvariablen und Pfade aus seinen Konfigurationsdateien, die ein Pull Request ändern kann.
  - Renovate liest das Alter einer Action-Version aus Git-Daten, die bestimmt, wer den Tag setzt. Die Wartezeit von drei Tagen gilt für Actions deshalb nur, wenn die Version ein Release auf GitHub hat. Actions werden nie automatisch übernommen.
  - gitleaks liest eine Datei `.gitleaksignore` von sich aus, und eine Zeile darin schaltet jeden Fund ab. Hooks und CI weisen die Datei zurück.
  - Die Action von OpenSSF Scorecard lädt ihr Container-Image über einen Tag, nicht über einen Digest.
  - zizmor prüft Versionskommentare und bekannte Schwachstellen der Actions nur mit Netz, also nur in CI, nicht im lokalen `pnpm ci:local`.
  - Renovate trägt für eine Sicherheitsaktualisierung die Ausnahme vom Mindestalter selbst ein. Die Prüfung der pnpm-Einstellungen verlangt dazu Datum und Grund, sonst bleibt der Pull Request rot.
  - dependency-cruiser findet ohne einen TypeScript-Compiler, den es lesen kann, keine Module und meldet trotzdem Erfolg, ebenso mit dem JSON-Reporter bei Verstössen. Der Reporter von `pnpm check:arch` endet mit der Zahl der Verstösse als Code, also bei genau 256 Verstössen mit 0. Die Tests prüfen deshalb selbst, dass TypeScript verfügbar ist, dass jede Quelldatei gelesen wird und dass die Pakete keinen einzigen Verstoss haben.
