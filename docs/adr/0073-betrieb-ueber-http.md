# ADR 0073: Betrieb über HTTP: eine Instanz je Anfrage, ältere Clients, Rückfragen, Grenzen und Zustand, ergänzt ADR 0022, ADR 0029, ADR 0051 und ADR 0053

- Status: Vorgeschlagen
- Datum: 16.11.2026
- Fällt vor: Phase 7

## Kontext

Ab Phase 7 bedient Ecclium MCP-Clients auch über HTTP. [ADR 0053](0053-mcp-sdk-und-instanzmodell.md) legt den Rahmen fest: `createMcpHandler` aus `@modelcontextprotocol/server` erzeugt über HTTP eine Instanz je Anfrage, Antworten gehen im JSON-Modus, und der Adapter `@modelcontextprotocol/hono` kommt in einer Version dazu, die zum gepinnten Serverpaket passt. Drei Fragen liess es für Phase 7 offen, und andere ADRs haben weitere an den Betrieb über HTTP gebunden:

- **Ältere Clients:** `createMcpHandler` bedient Clients mit einer Protokollversion bis 2025-11-25 ohne Sitzung. Eine solche Instanz kennt die Fähigkeiten des Clients nicht, eine Rückfrage über Elicitation geht dann nicht. Zur Wahl stehen `stateless` und `reject` ([ADR 0053](0053-mcp-sdk-und-instanzmodell.md), [ADR 0029](0029-write-guard.md)).
- **Ströme:** `subscriptions/listen` beantwortet das SDK auch im JSON-Modus über SSE, und weil `McpServer` in der Voreinstellung `listChanged` deklariert, bliebe ein solcher Strom offen ([ADR 0053](0053-mcp-sdk-und-instanzmodell.md)). Der Mount meldet schon über stdio `listChanged: false` für Tools und Prompts (`packages/core/src/mcp/mount.ts`). Offen ist nur, wie der Server über HTTP mit `subscriptions/listen` umgeht. Eine Stelle je Methode vor dem Handler bietet das SDK nicht ([Befunde zum MCP-SDK](../research/mcp-sdk-und-elicitation.md)).
- **Schlüssel des `requestState`:** Über stdio entsteht er zufällig je Prozess. Offen ist, woher er über HTTP kommt, wenn mehrere Prozesse die Runden einer Rückfrage bedienen könnten ([ADR 0029](0029-write-guard.md), [ADR 0053](0053-mcp-sdk-und-instanzmodell.md)).
- **Offene Pläne:** [ADR 0029](0029-write-guard.md) verlangt vor HTTP eine Obergrenze offener Pläne je Mandant und Akteur unter der des Prozesses (100), sonst kann ein Prinzipal mit 100 Plänen die der anderen für 600 Sekunden sperren.
- **DNS-Rebinding:** Die MCP-Spezifikation 2026-07-28 verlangt, die Kopfzeile `Origin` jeder Verbindung zu prüfen und lokal nur an localhost zu binden (Seite «Streamable HTTP», Abschnitt «Security & Endpoint»). Das Threat Model führt das als T21, mit dem Vermerk, dass ein ADR dazu vor dem Code für HTTP folgt.
- **Ort des Ports:** Der Server über HTTP lauscht auf einem Port und braucht dafür einen eigenen Ort mit Begründung ([ADR 0022](0022-paketzuschnitt.md)). Heute öffnet nur der Ort `egress` Verbindungen.
- **Zustand:** Über HTTP kommen ein Rate-Limit je Token und je Adresse, ein Cache für `/readyz` (Threat Model T20) und, im OAuth-Modus, die Schlüssel des Anmeldediensts dazu. Jeder Zustand über eine Anfrage hinaus braucht eine benannte Stelle ([ADR 0051](0051-zustand-zwischen-anfragen.md)).
- **Frist für den `TenantResolver`:** Der Mount wartet heute ohne eigene Frist auf ihn. Über stdio antwortet er aus der Konfiguration. Spätestens über HTTP braucht er eine Frist (`docs/STATUS.md`, «Offen»).

Fakten, geprüft am 16.11.2026:

- Ein versiegelter Plan liegt im `PlanStore` nur im Arbeitsspeicher des Prozesses, der ihn geplant hat, höchstens 100 je Prozess und 600 Sekunden lang. Verbrauchte Nonces liegen im `NonceStore`, ebenfalls nur im Arbeitsspeicher ([ADR 0029](0029-write-guard.md)).
- Das Serverpaket bringt Middleware für HTTP mit (`hostHeaderValidationResponse`, `originValidationResponse`, `requireBearerAuth`, `oauthMetadataResponse`). Sie prüft eine Anfrage vor `createMcpHandler`, nicht je Methode ([Befunde zum MCP-SDK](../research/mcp-sdk-und-elicitation.md)).
- Claude Code verhandelt über stdio seit Version 2.1.292 standardmässig 2026-07-28 ([Befunde zum MCP-SDK](../research/mcp-sdk-und-elicitation.md)). Welche Version claude.ai und ChatGPT über HTTP senden, ist nicht geprüft.
- In der Registry von npm verlangt `@modelcontextprotocol/hono` 2.0.2 (02.10.2026, Apache-2.0, mit Herkunftsnachweis) `@modelcontextprotocol/server` ab 2.3.0 und `hono` ab 4.11.4. `hono` 4.13.18 und `@hono/node-server` 2.1.8 stehen unter MIT, ohne Abhängigkeiten, mit Herkunftsnachweis. Gepinnt ist `@modelcontextprotocol/server` 2.3.1, neu ist 2.4.0 vom 23.10.2026.

## Optionen

Zu den drei offenen Fragen aus ADR 0053 gibt es je zwei Wege:

1. **Ältere Clients:** `stateless` bedient sie ohne Rückfrage, `reject` weist sie mit dem Fehler -32022 und den unterstützten Versionen ab. Mit `reject` könnte ein Client, der über HTTP noch 2025-11-25 spricht, Ecclium gar nicht nutzen.
2. **Ströme:** Ströme über SSE zulassen hält Verbindungen offen, die ein Reverse-Proxy, das Rate-Limit und die Grenzen der Anfrage gesondert behandeln müssten. Sie abzuweisen kostet nichts, solange sich die Liste der Tools nach dem Start nicht ändert.
3. **Schlüssel des `requestState`:** Ein Schlüssel aus einer Datei mit Rotation liesse mehrere Prozesse die Runden einer Rückfrage bedienen. Er brächte ein Geheimnis mehr und erlaubte nach einem Neustart eine Wiederholung innerhalb von 600 Sekunden, ausser eine Epoche je Start käme dazu. Ein Schlüssel je Prozess wie über stdio kommt ohne Geheimnis aus, verlangt aber, dass beide Runden denselben Prozess treffen.

## Entscheid

- **Einstieg:** `ecclium serve-http` startet den Server über HTTP. Hono mit `@hono/node-server` nimmt die Anfragen an, `createMcpHandler` erzeugt je Anfrage eine Instanz, aus derselben Fabrik und mit denselben Wachen wie über stdio ([ADR 0059](0059-gebuendelter-code-im-mcp-sdk.md)). Antworten gehen im JSON-Modus. Server, Kernpaket und Adapter werden nur gemeinsam aktualisiert ([ADR 0053](0053-mcp-sdk-und-instanzmodell.md)); eine neue Version des Servers braucht vorher die Prüfung des gebündelten Codes nach [ADR 0059](0059-gebuendelter-code-im-mcp-sdk.md).
- **Kein Betrieb ohne Anmeldung** ([ADR 0037](0037-anmeldung-am-server.md)): `serve-http` startet nur mit statischen Bearer-Tokens oder im OAuth-Modus ([ADR 0074](0074-bearer-tokens-und-oauth-pruefung.md)) und nur mit `ECCLIUM_STATE_DIR`, weil Audit-Datei, Lesebudget und Zählung der Tokens dort liegen. Sonst endet der Start mit 78. Ausnahme nur für eine Probe, nie für Ecclium: Eine Attrappe aus `testkit`, ohne ChurchTools, ohne Daten und mit einem leeren Tool, darf für die Dauer einer Probe öffentlich und ohne Anmeldung erreichbar sein, damit sich festhalten lässt, welche Kopfzeile und welche Version im Körper claude.ai und ChatGPT senden. Sie hält nur diese beiden Werte fest und ist kein Betrieb von Ecclium.
- **Ort `ingress` (ergänzt ADR 0022):** Nur `packages/server/src/http/` öffnet einen Port und importiert `@hono/node-server`. Eine Regel für dependency-cruiser und ESLint hält das fest, mit einer Beispieldatei, die rot wird. Tests rufen die Anwendung im Prozess über ihre Funktion `fetch` auf, ohne Socket; ein einzelner Test bindet an `127.0.0.1`, was die Netzsperre der Tests erlaubt ([ADR 0052](0052-tests-ohne-aussenverbindung.md)).
- **Ältere Clients:** Ecclium bedient sie ohne Sitzung (`stateless`). Lesen geht wie mit jedem Client. Eine Rückfrage zur Bestätigung gibt es für sie nicht, ein Schreibvorgang geht in die Freigabe-Warteschlange, und das Echo gilt nur, wenn der Betreiber `ECCLIUM_WRITE_CONFIRMATION=echo-allowed` ausdrücklich setzt ([ADR 0029](0029-write-guard.md)). Dieser Punkt ist vorläufig: Die Probe an der Attrappe und der Client-Test in Phase 7 halten fest, welche Version jeder Client über HTTP sendet. Braucht ein Client etwas anderes, löst ein neues ADR diesen Punkt ab.
- **Keine Ströme:** `subscriptions/listen` weist der Ort `ingress` mit einem Fehler ab, bevor die Anfrage `createMcpHandler` erreicht, anhand der Methode im geprüften Körper. `listChanged` bleibt für Tools und Prompts `false`. Welche Tools es gibt, steht beim Start fest; welche davon ein Client sieht, hängt nur noch von den Scopes seines Tokens ab ([ADR 0074](0074-bearer-tokens-und-oauth-pruefung.md)). Ändern sich die Scopes eines Tokens, sieht der Client die neue Liste, wenn er sie neu abruft, und ein Aufruf ausserhalb seiner Scopes endet mit 403. Jede Antwort ist JSON, kein Strom bleibt offen, und eine Anfrage `GET` an den Pfad für MCP endet mit 405.
- **Schlüssel des `requestState`:** zufällig je Prozess, 32 Bytes, nie gespeichert, wie über stdio. Im Self-Hosting läuft genau ein Prozess des Servers je Installation. Pläne und Nonces liegen nur im Arbeitsspeicher dieses Prozesses, eine zweite Runde muss ihn also ohnehin treffen. Ein Neustart beendet offene Rückfragen, und keine Runde von vorher gilt danach. Mehrere Prozesse brauchen gemeinsame Speicher für Pläne und Nonces und einen gemeinsamen Schlüssel; das ist Sache eines Ersatzes der Ports durch ein Plugin, mit eigenem ADR. Damit ist der offene Punkt aus ADR 0029 und ADR 0053 entschieden. Eine Datei `request_state_key` gibt es nicht.
- **Offene Pläne je Akteur:** höchstens 20 offene Pläne je Mandant und Akteur, unter den 100 je Prozess. Darüber endet ein neuer Plan mit `policy_denied`, bis ältere ablaufen. Das gilt über stdio und HTTP gleich.
- **Host und Origin (T21):** Die Kopfzeile `Host` muss einem Eintrag in `ECCLIUM_ALLOWED_HOSTS` gleichen, einem Namen mit oder ohne Port. Ohne die Variable gelten nur die Namen für Loopback mit dem Port des Servers. Eine Kopfzeile `Origin`, wenn vorhanden, muss genau einen erlaubten Host mit `https` nennen, für Loopback auch `http`. Sonst antwortet der Server mit 403. Ob die Prüfung eigener Code im Ort `ingress` ist oder die Middleware des SDK, entscheidet der Bau; die Regel gilt gleich.
- **Bindung:** voreingestellt an `127.0.0.1`. An eine andere Adresse, etwa `0.0.0.0` im Container, bindet der Server nur zusammen mit `ECCLIUM_ALLOWED_HOSTS`, sonst endet der Start mit 78. TLS endet am Reverse-Proxy, nicht im Prozess.
- **Grenzen der Anfrage:** Körper höchstens 1 MiB (sonst 413), JSON höchstens 64 Ebenen tief (sonst 400), Fristen für Kopfzeilen und Anfrage, keine Kopfzeile für CORS, auch nicht auf `OPTIONS`. Eine Kopfzeile `MCP-Protocol-Version`, die nicht zur Version im Körper passt, endet mit 400, wie es die Spezifikation verlangt. Dieser Punkt ist vorläufig wie der zu älteren Clients: Ein öffentlicher Fehlerbericht vom 10.09.2026 nennt Claude Desktop und Claude Code, die über Connectors von claude.ai die Kopfzeile 2025-11-25 mit 2026-07-28 im Körper senden, und ein Server ohne Sitzung wies sie deshalb ab (Repository `anthropics/claude-code`, Issue 93290, am 15.11.2026 ohne Fix geschlossen, geprüft am 16.11.2026). Den Beleg liefert früh die Probe an der Attrappe. Vorbereitet ist eine Ersatzregel: Unterstützt der Server beide Versionen, gilt die im Körper, die Abweichung zählt in den Metriken, und die Anfrage wird bearbeitet. Sie wiche bewusst von der Spezifikation ab und gilt erst, wenn die Probe oder der Client-Test zeigt, dass ein zugesagter Client sonst abgewiesen wird; dann steht das mit dem Beleg in diesem ADR, solange es vorgeschlagen ist, sonst in einem neuen.
- **Rate-Limit:** höchstens 120 Anfragen je Minute und angemeldetem Prinzipal und höchstens 10 gescheiterte Anmeldungen je Minute und Adresse eines Clients, danach 429 mit `Retry-After`. Als Adresse gilt die des Sockets. Die Adresse aus `X-Forwarded-For` zählt nur, wenn die direkte Gegenstelle in `ECCLIUM_TRUSTED_PROXIES` steht, voreingestellt leer, im Bundle für das Self-Hosting der Reverse-Proxy. Sonst sperrten hinter einem Proxy zehn Fehlversuche irgendeiner Person alle aus, und eine Kopfzeile eines Clients könnte die Sperre umgehen. Eine Anfrage ganz ohne Token und ein JWT, das nur abgelaufen ist, zählen nicht als gescheiterte Anmeldung: Mit ihnen beginnt ein Client eine Anmeldung oder erneuert sein Token, und alle Nutzer von claude.ai kommen aus wenigen Adressen des Anbieters. Gegen Scanner bleibt die Grenze für Tokens mit falscher Form, Prüfsumme oder Signatur. Was ein Fehlversuch im Audit hinterlässt, legt [ADR 0074](0074-bearer-tokens-und-oauth-pruefung.md) fest.
- **Frist für den `TenantResolver`:** zehn Sekunden über stdio und HTTP. Danach endet der Aufruf mit `upstream`, wie wenn der Resolver einen Fehler meldet. Ein neuer Code entsteht dafür nicht, weil die Codes ein Vertrag mit Plugins und Lesern des Audits sind.
- **`/healthz`, `/readyz` und `/metrics`:** `/healthz` antwortet ohne Abhängigkeit, solange der Prozess Anfragen annimmt. `/readyz` fragt ChurchTools je Mandant höchstens alle 60 Sekunden mit `GET /api/whoami` und antwortet mit 200 oder 503, ohne Einzelheiten. `/metrics` antwortet auf einem eigenen Port nur, wenn der Betreiber ihn setzt, im Textformat von Prometheus mit eigenem Code wie beim Runner, ohne Inhalte. Der Reverse-Proxy des Bundles gibt nur den Pfad für MCP, `/healthz` und `/.well-known/oauth-protected-resource` frei, so dass im Bundle niemand von aussen über `/readyz` Anfragen an ChurchTools auslöst (T20). Wer ohne das Bundle an eine andere Adresse als Loopback bindet, schützt `/readyz` selbst; in jedem Fall begrenzt der Cache die Anfragen auf eine je Minute und Mandant.
- **Zustand über eine Anfrage hinaus (ergänzt ADR 0051):** Drei weitere benannte Ausnahmen im Arbeitsspeicher, zusätzlich zum Pool der Verbindungen und zum Zähler der Drosselung:
  - die Zähler des Rate-Limits je Prinzipal und je Adresse eines Clients;
  - das Ergebnis von `/readyz` je Mandant für 60 Sekunden, nur bereit oder nicht bereit;
  - im OAuth-Modus die öffentlichen Schlüssel des Anmeldediensts je Aussteller ([ADR 0074](0074-bearer-tokens-und-oauth-pruefung.md)).

  Keine trägt Inhalte aus ChurchTools oder Zugangsdaten, ein Neustart setzt sie zurück, und zwei Prozesse teilen nichts. Zwei weichen von ADR 0051 ab, mit Grund: Die Zähler je Adresse eines Clients gehören zu keinem Mandanten, weil vor der Anmeldung keiner feststeht; sie tragen nur die Adresse und eine Zahl. Das Ergebnis von `/readyz` gilt je Mandant, ohne Akteur und Route, weil es nur bereit oder nicht bereit trägt und für jeden Akteur gleich ist. Die Schlüssel gelten je Aussteller.

- **Audit über HTTP:** wie über stdio zuerst in die Audit-Datei und danach als Kopie über den Logger auf stderr, ohne Kennungen in der Kopie ([ADR 0028](0028-audit-ereignis-und-datei-sink.md)). Die Logzeile eines Prompts nennt über HTTP den Mandanten ([ADR 0065](0065-mcp-prompts-als-feste-vorlagen.md)).
- **Synchrone Zugriffe auf Dateien:** Audit-Datei, `QuotaStore` und Sperrdateien schreiben weiter synchron. Das hält heute drei Regeln einfach: die Reihenfolge der Kette im Audit, die Zeile auf der Platte vor dem Ergebnis eines Tools mit `sensitivity: special` und das Zählen des Lesebudgets. Über HTTP laufen Anfragen mehrerer Prinzipale im selben Prozess. Eine Messung mit 20 Clients parallel und ein Test mit zwei Prinzipalen gleichzeitig zeigen, ob das reicht. Blockiert die Event-Loop dabei im 99. Perzentil länger als 100 Millisekunden, kommen die betroffenen Wege auf asynchrone Zugriffe, ohne eine der drei Regeln aufzugeben. Das Ergebnis steht unter «Umsetzung».

## Konsequenzen

- Clients mit älterer Protokollversion lesen über HTTP wie alle anderen, schreiben aber nur über die Freigabe-Warteschlange oder, mit ausdrücklich gesetztem `echo-allowed`, über das Echo. Über die Warteschlange braucht eine Person, die schreiben will, einen Betreiber, der mit `ecclium queue approve` freigibt.
- Ein Neustart des Servers beendet offene Rückfragen. Der Client sieht einen Fehler, die Person stellt die Aufgabe neu.
- Der freie Kern skaliert über HTTP nicht über mehrere Prozesse. Wer das braucht, ersetzt die drei Zustands-Ports und den Schlüssel, im gehosteten Betrieb mit dem Pro-Modul.
- Ein Client, der auf Änderungen der Liste wartet, erhält einen Fehler statt eines Stroms. Neue Tools gibt es ohnehin nur nach einem Neustart.
- Hinter einem Reverse-Proxy muss `ECCLIUM_TRUSTED_PROXIES` stimmen, sonst zählt das Rate-Limit nur die Adresse des Proxys. Das Bundle setzt sie, eine eigene Installation muss es selbst tun, und `ecclium doctor` meldet eine Bindung an eine andere Adresse als Loopback ohne vertrauten Proxy als Befund.
- Restrisiken:
  - Clients ausserhalb eines Browsers senden oft kein `Origin`. Gegen DNS-Rebinding hilft dann die Prüfung von `Host`; ein Client mit gültigem Token und gefälschtem `Host` ist kein Angriff über einen Browser.
  - Die Zähler des Rate-Limits und der Cache von `/readyz` beginnen nach einem Neustart bei null.
  - Bis zur Messung ist offen, wie sich synchrone Zugriffe unter Last verhalten.
  - Die Obergrenze je Akteur verhindert nicht, dass fünf Akteure mit je 20 offenen Plänen die 100 des Prozesses füllen und die übrigen für bis zu 600 Sekunden sperren. Dafür braucht es fünf angemeldete Prinzipale mit dem Scope `write`.
  - Ob die Kopfzeile der Protokollversion bei allen Clients zur Version im Körper passt, zeigt erst der Client-Test. Bis dahin kann die Regel einen Client abweisen, der sonst funktionieren würde.
