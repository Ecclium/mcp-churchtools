# ADR 0073: Betrieb über HTTP: eine Instanz je Anfrage, ältere Clients, Rückfragen, Grenzen und Zustand, ergänzt ADR 0022, ADR 0029, ADR 0051 und ADR 0053

- Status: Vorgeschlagen
- Datum: 16.11.2026
- Fällt vor: Phase 7

## Kontext

Ab Phase 7 bedient Ecclium MCP-Clients auch über HTTP. [ADR 0053](0053-mcp-sdk-und-instanzmodell.md) legt den Rahmen fest: `createMcpHandler` aus `@modelcontextprotocol/server` erzeugt über HTTP eine Instanz je Anfrage, Antworten gehen im JSON-Modus, und der Adapter `@modelcontextprotocol/hono` kommt in einer Version dazu, die zum gepinnten Serverpaket passt. Drei Fragen liess es für Phase 7 offen, und andere ADRs haben weitere an den Betrieb über HTTP gebunden:

- **Ältere Clients:** `createMcpHandler` bedient Clients mit einer Protokollversion bis 2025-11-25 ohne Sitzung. Eine solche Instanz kennt die Fähigkeiten des Clients nicht, eine Rückfrage über Elicitation geht dann nicht. Zur Wahl stehen `stateless` und `reject` ([ADR 0053](0053-mcp-sdk-und-instanzmodell.md), [ADR 0029](0029-write-guard.md)).
- **Ströme:** `subscriptions/listen` beantwortet das SDK auch im JSON-Modus über SSE, und weil `McpServer` in der Voreinstellung `listChanged` deklariert, bliebe ein solcher Strom offen ([ADR 0053](0053-mcp-sdk-und-instanzmodell.md)). Der Mount meldet schon über stdio `listChanged: false` für Tools und Prompts (`packages/core/src/mcp/mount.ts`). Offen ist nur, wie der Server über HTTP mit `subscriptions/listen` umgeht. Eine Stelle je Methode vor dem Handler bietet das SDK nicht ([Befunde zum MCP-SDK](../research/mcp-sdk-und-elicitation.md)).
- **Schlüssel des `requestState`:** Über stdio entsteht er zufällig je Prozess. Offen ist, woher er über HTTP kommt, wenn mehrere Prozesse die Runden einer Rückfrage bedienen könnten ([ADR 0029](0029-write-guard.md), [ADR 0053](0053-mcp-sdk-und-instanzmodell.md)).
- **Offene Pläne:** [ADR 0029](0029-write-guard.md) verlangt vor HTTP eine Obergrenze offener Pläne je Mandant und Akteur unter der des Prozesses (100), sonst kann ein Prinzipal mit 100 Plänen die der anderen für 600 Sekunden sperren.
- **DNS-Rebinding:** Die MCP-Spezifikation 2026-07-28 verlangt, die Kopfzeile `Origin` jeder Verbindung zu prüfen und lokal nur an localhost zu binden (Seite «Streamable HTTP», Abschnitt «Security & Endpoint»). Das Threat Model führt das als T21, mit dem Vermerk, dass ein ADR dazu vor dem Code für HTTP folgt.
- **Ort des Ports:** Der Server über HTTP lauscht auf einem Port und braucht dafür einen eigenen Ort mit Begründung ([ADR 0022](0022-paketzuschnitt.md)). Heute öffnet nur der Ort `egress` Verbindungen.
- **Zustand:** Über HTTP kommen ein Rate-Limit je Token und je Adresse, ein Cache für `/readyz` (Threat Model T20) und, im OAuth-Modus, die Schlüssel des Anmeldediensts dazu. Jeder Zustand über eine Anfrage hinaus braucht eine benannte Stelle ([ADR 0051](0051-zustand-zwischen-anfragen.md)).
- **Frist für den `TenantResolver`:** Der Mount wartet heute ohne eigene Frist auf ihn. Über stdio antwortet er aus der Konfiguration. Spätestens über HTTP braucht er eine Frist (`docs/STATUS.md`, «Offen»).

Fakten, geprüft am 16.11.2026:

- Ein versiegelter Plan liegt im `PlanStore` nur im Arbeitsspeicher des Prozesses, der ihn geplant hat, höchstens 100 je Prozess und 600 Sekunden lang. Verbrauchte Nonces liegen im `NonceStore`, ebenfalls nur im Arbeitsspeicher ([ADR 0029](0029-write-guard.md)).
- Das Serverpaket bringt Middleware für HTTP mit (`hostHeaderValidationResponse`, `originValidationResponse`, `requireBearerAuth`, `oauthMetadataResponse`). Sie prüft eine Anfrage vor `createMcpHandler`, nicht je Methode ([Befunde zum MCP-SDK](../research/mcp-sdk-und-elicitation.md)).
- Claude Code verhandelt über stdio seit Version 2.1.292 standardmässig 2026-07-28 ([Befunde zum MCP-SDK](../research/mcp-sdk-und-elicitation.md)). Über HTTP sendet Claude Code 2.1.319 in beiden Ären Kopfzeilen, die zum Körper passen, und das SDK 2.3.1 nimmt sie an ([MCP-Clients über HTTP](../research/mcp-clients-ueber-http.md), Probe an der Attrappe auf Loopback). An der Attrappe über einen Tunnel sendet ChatGPT im Developer Mode (`openai-mcp` 1.0.0) die Ära 2026 mit allen Kopfzeilen passend, claude.ai (`Anthropic` 1.0.0) `initialize` der Ära 2025 mit Kopfzeile und Körper 2025-11-25. Weiter kam claude.ai wegen eines offenen Fehlers auf seiner Seite nicht. Kein Client sendet `Origin`.
- In der Registry von npm verlangt `@modelcontextprotocol/hono` 2.0.2 (02.10.2026, Apache-2.0, mit Herkunftsnachweis) `@modelcontextprotocol/server` ab 2.3.0 und `hono` ab 4.11.4. `hono` 4.13.18 und `@hono/node-server` 2.1.8 stehen unter MIT, ohne Abhängigkeiten, mit Herkunftsnachweis. Gepinnt ist `@modelcontextprotocol/server` 2.3.1, neu ist 2.4.0 vom 23.10.2026.

## Optionen

Zu den drei offenen Fragen aus ADR 0053 gibt es je zwei Wege:

1. **Ältere Clients:** `stateless` bedient sie ohne Rückfrage, `reject` weist sie mit dem Fehler -32022 und den unterstützten Versionen ab. Mit `reject` könnte ein Client, der über HTTP noch 2025-11-25 spricht, Ecclium gar nicht nutzen.
2. **Ströme:** Ströme über SSE zulassen hält Verbindungen offen, die ein Reverse-Proxy, das Rate-Limit und die Grenzen der Anfrage gesondert behandeln müssten. Sie abzuweisen kostet nichts, solange sich die Liste der Tools nach dem Start nicht ändert.
3. **Schlüssel des `requestState`:** Ein Schlüssel aus einer Datei mit Rotation liesse mehrere Prozesse die Runden einer Rückfrage bedienen. Er brächte ein Geheimnis mehr und erlaubte nach einem Neustart eine Wiederholung innerhalb von 600 Sekunden, ausser eine Epoche je Start käme dazu. Ein Schlüssel je Prozess wie über stdio kommt ohne Geheimnis aus, verlangt aber, dass beide Runden denselben Prozess treffen.

## Entscheid

- **Einstieg:** `ecclium serve-http` startet den Server über HTTP. Eine Anwendung mit Hono nimmt die Anfragen an, über eine eigene Brücke auf `node:http` im Ort `ingress` statt `@hono/node-server` (siehe «Umsetzung»), und `createMcpHandler` erzeugt je Anfrage eine Instanz, aus derselben Fabrik und mit denselben Wachen wie über stdio ([ADR 0059](0059-gebuendelter-code-im-mcp-sdk.md)). Antworten gehen im JSON-Modus. Server, Kernpaket und Adapter werden nur gemeinsam aktualisiert ([ADR 0053](0053-mcp-sdk-und-instanzmodell.md)); eine neue Version des Servers braucht vorher die Prüfung des gebündelten Codes nach [ADR 0059](0059-gebuendelter-code-im-mcp-sdk.md).
- **Kein Betrieb ohne Anmeldung** ([ADR 0037](0037-anmeldung-am-server.md)): `serve-http` startet nur mit statischen Bearer-Tokens oder im OAuth-Modus ([ADR 0074](0074-bearer-tokens-und-oauth-pruefung.md)) und nur mit `ECCLIUM_STATE_DIR`, weil Audit-Datei, Lesebudget und Zählung der Tokens dort liegen. Sonst endet der Start mit 78. Ausnahme nur für eine Probe, nie für Ecclium: Eine Attrappe ausserhalb der Pakete, bei den Proben unter `scripts/spike/`, ohne ChurchTools, ohne Daten und mit einem leeren Tool, darf für die Dauer einer Probe öffentlich und ohne Anmeldung erreichbar sein, damit sich festhalten lässt, welche Kopfzeile und welche Version im Körper claude.ai und ChatGPT senden. Sie hält nur fest, welche Kopfzeilen des Protokolls und welche Version ein Client sendet, wie er sich nennt und wie das SDK antwortet, als feste Wörter und Werte in fester Form, nie Adressen, den Host, Pfade, weitere Kopfzeilen oder Inhalte, und sie ist kein Betrieb von Ecclium. Gebaut ist sie als `scripts/spike/14-protocol-version.mts`: Sie bindet nur an `127.0.0.1`, ein Tunnel auf demselben Rechner macht sie öffentlich, und sie endet nach höchstens 120 Minuten oder 500 Anfragen von selbst. Name und Version eines Clients wählt dieser selbst; sie erscheinen nur in einer engen Form, in die weder ein Host noch eine IPv4-Adresse passt. Dafür steht das Serverpaket des SDK auch unter den Entwicklungsabhängigkeiten der Wurzel, in derselben Version wie in den Paketen. Der Nachweis aus [ADR 0059](0059-gebuendelter-code-im-mcp-sdk.md) gilt für die Attrappe: Sie ruft weder `fromJsonSchema` noch `elicitInput` auf, setzt denselben verweigernden Validator wie der Mount, und ihr Test zählt über beide Ären mit feindlichen Eingaben keinen Aufruf von `fast-uri`.
- **Ort `ingress` (ergänzt ADR 0022):** Nur `packages/server/src/http/` öffnet einen Port und importiert `hono` und den Adapter `@modelcontextprotocol/hono`. Eine Regel für dependency-cruiser und ESLint hält das fest, mit einer Beispieldatei, die rot wird. Tests rufen die Anwendung im Prozess über ihre Funktion `fetch` auf, ohne Socket; eine einzelne Testdatei bindet an `127.0.0.1`, was die Netzsperre der Tests erlaubt ([ADR 0052](0052-tests-ohne-aussenverbindung.md)).
- **Ältere Clients:** Ecclium bedient sie ohne Sitzung (`stateless`). Lesen geht wie mit jedem Client. Eine Rückfrage zur Bestätigung gibt es für sie nicht, ein Schreibvorgang geht in die Freigabe-Warteschlange, und das Echo gilt nur, wenn der Betreiber `ECCLIUM_WRITE_CONFIRMATION=echo-allowed` ausdrücklich setzt ([ADR 0029](0029-write-guard.md)). Die Probe an der Attrappe bestätigt den Punkt am 16.11.2026: claude.ai spricht über HTTP die Ära 2025, mit `reject` könnte es Ecclium nicht nutzen ([MCP-Clients über HTTP](../research/mcp-clients-ueber-http.md)). Der Client-Test in Phase 7 hält fest, welche Version jeder Client über den Server von Ecclium sendet. Braucht ein Client etwas anderes, löst ein neues ADR diesen Punkt ab.
- **Keine Ströme:** `subscriptions/listen` weist der Ort `ingress` mit einem Fehler ab, bevor die Anfrage `createMcpHandler` erreicht, anhand der Methode im geprüften Körper. Den Körper liest er dafür wie das SDK, das ein Byte Order Mark am Anfang entfernt, oder er übergibt ihn dem SDK gelesen; sonst ginge eine solche Anfrage an der Prüfung vorbei ([MCP-Clients über HTTP](../research/mcp-clients-ueber-http.md)). `listChanged` bleibt für Tools und Prompts `false`. Welche Tools es gibt, steht beim Start fest; welche davon ein Client sieht, hängt nur noch von den Scopes seines Tokens ab ([ADR 0074](0074-bearer-tokens-und-oauth-pruefung.md)). Ändern sich die Scopes eines Tokens, sieht der Client die neue Liste, wenn er sie neu abruft, und ein Aufruf ausserhalb seiner Scopes endet mit 403. Jede Antwort ist JSON, kein Strom bleibt offen, und eine Anfrage `GET` an den Pfad für MCP endet mit 405. Den Weg der Ära 2025 beantwortet das SDK auch im JSON-Modus als Strom von Server-Sent Events, der sich nach einer Nachricht schliesst. Ein Proxy oder Tunnel ohne Ströme hält eine solche Antwort zurück, an der Attrappe so für claude.ai beobachtet. Der Ort `ingress` gibt deshalb einen solchen Strom mit genau einer Nachricht als JSON weiter, was die Spezifikation einem Client erlaubt, der beides annimmt; einen Strom mit mehr als einer Nachricht reicht er unverändert weiter.
- **Schlüssel des `requestState`:** zufällig je Prozess, 32 Bytes, nie gespeichert, wie über stdio. Im Self-Hosting läuft genau ein Prozess des Servers je Installation. Pläne und Nonces liegen nur im Arbeitsspeicher dieses Prozesses, eine zweite Runde muss ihn also ohnehin treffen. Ein Neustart beendet offene Rückfragen, und keine Runde von vorher gilt danach. Mehrere Prozesse brauchen gemeinsame Speicher für Pläne und Nonces und einen gemeinsamen Schlüssel; das ist Sache eines Ersatzes der Ports durch ein Plugin, mit eigenem ADR. Damit ist der offene Punkt aus ADR 0029 und ADR 0053 entschieden. Eine Datei `request_state_key` gibt es nicht.
- **Offene Pläne je Akteur:** höchstens 20 offene Pläne je Mandant und Akteur, unter den 100 je Prozess. Darüber endet ein neuer Plan mit `policy_denied`, bis ältere ablaufen. Das gilt über stdio und HTTP gleich.
- **Host und Origin (T21):** Die Kopfzeile `Host` muss einem Eintrag in `ECCLIUM_ALLOWED_HOSTS` gleichen, einem Namen mit oder ohne Port. Ohne die Variable gelten nur die Namen für Loopback mit dem Port des Servers. Eine Kopfzeile `Origin`, wenn vorhanden, muss genau einen erlaubten Host mit `https` nennen, für Loopback auch `http`. Sonst antwortet der Server mit 403. Ob die Prüfung eigener Code im Ort `ingress` ist oder die Middleware des SDK, entscheidet der Bau; die Regel gilt gleich.
- **Bindung:** voreingestellt an `127.0.0.1`. An eine andere Adresse, etwa `0.0.0.0` im Container, bindet der Server nur zusammen mit `ECCLIUM_ALLOWED_HOSTS`, sonst endet der Start mit 78. TLS endet am Reverse-Proxy, nicht im Prozess.
- **Grenzen der Anfrage:** Körper höchstens 1 MiB (sonst 413), JSON höchstens 64 Ebenen tief (sonst 400), Fristen für Kopfzeilen und Anfrage, keine Kopfzeile für CORS, auch nicht auf `OPTIONS`. Eine Kopfzeile `MCP-Protocol-Version`, die nicht zur Version im Körper passt, endet mit 400, wie es die Spezifikation verlangt. Dieser Punkt ist vorläufig wie der zu älteren Clients: Ein öffentlicher Fehlerbericht vom 10.09.2026 nennt Claude Desktop und Claude Code, die über Connectors von claude.ai die Kopfzeile 2025-11-25 mit 2026-07-28 im Körper senden, und ein Server ohne Sitzung wies sie deshalb ab (Repository `anthropics/claude-code`, Issue 93290, am 15.11.2026 ohne Fix geschlossen, geprüft am 16.11.2026). Den Beleg liefert früh die Probe an der Attrappe. Vorbereitet ist eine Ersatzregel: Unterstützt der Server beide Versionen, gilt die im Körper, die Abweichung zählt in den Metriken, und die Anfrage wird bearbeitet. Weil das SDK eine solche Abweichung selbst abweist, gleicht der Ort `ingress` die Kopfzeile dann vor `createMcpHandler` an die Version im Körper an. Sie wiche bewusst von der Spezifikation ab und gilt erst, wenn die Probe oder der Client-Test zeigt, dass ein zugesagter Client sonst abgewiesen wird; dann steht das mit dem Beleg in diesem ADR, solange es vorgeschlagen ist, sonst in einem neuen. Die Ersatzregel deckt nur die abweichende Version. Das SDK 2.3.1 weist eine Anfrage der Ära 2026 auch ohne `MCP-Protocol-Version`, ohne `Mcp-Method` oder mit einer anderen Methode darin ab, `tools/call` ohne passendes `Mcp-Name`, `initialize` mit einer Kopfzeile der Ära 2026 und eine Kopfzeile der Ära 2026 ohne Umschlag im Körper ([MCP-Clients über HTTP](../research/mcp-clients-ueber-http.md)). Die Probe hält deshalb auch diese Kopfzeilen fest. Scheitert ein zugesagter Client an einem dieser Fälle, ergänzt dieses ADR die Regel mit dem Beleg. Stand der Probe am 16.11.2026: ChatGPT, Claude Code und `initialize` von claude.ai senden passende Kopfzeilen, kein Client scheitert an einem dieser Fälle, und die Ersatzregel bleibt vorbereitet, nicht in Kraft. Was claude.ai nach `initialize` sendet, liess ein Fehler auf seiner Seite nicht beobachten; das prüft der Client-Test.
- **Rate-Limit:** höchstens 120 Anfragen je Minute und angemeldetem Prinzipal und höchstens 10 gescheiterte Anmeldungen je Minute und Adresse eines Clients, danach 429 mit `Retry-After`. Als Adresse gilt die des Sockets. Die Adresse aus `X-Forwarded-For` zählt nur, wenn die direkte Gegenstelle in `ECCLIUM_TRUSTED_PROXIES` steht, voreingestellt leer, im Bundle für das Self-Hosting der Reverse-Proxy. Sonst sperrten hinter einem Proxy zehn Fehlversuche irgendeiner Person alle aus, und eine Kopfzeile eines Clients könnte die Sperre umgehen. Eine Anfrage ganz ohne Token und ein JWT, das nur abgelaufen ist, zählen nicht als gescheiterte Anmeldung: Mit ihnen beginnt ein Client eine Anmeldung oder erneuert sein Token, und alle Nutzer von claude.ai kommen aus einem gemeinsamen Adressbereich des Anbieters. Sie erhalten 401 auch von einer gesperrten Adresse. Alle übrigen Gründe aus ADR 0074 zählen weiter, ausdrücklich auch ein unbekanntes Token, denn die Prüfsumme kann jeder selbst berechnen. Was ein Fehlversuch im Audit hinterlässt, legt [ADR 0074](0074-bearer-tokens-und-oauth-pruefung.md) fest.
- **Frist für den `TenantResolver`:** zehn Sekunden über stdio und HTTP. Danach endet der Aufruf mit `upstream`. Ein Fehler des Resolvers oder eine Antwort ohne Mandanten endet weiter mit `auth`, ein Abbruch durch den Client mit `network`. Ein neuer Code entsteht dafür nicht, weil die Codes ein Vertrag mit Plugins und Lesern des Audits sind.
- **`/healthz`, `/readyz` und `/metrics`:** `/healthz` antwortet ohne Abhängigkeit, solange der Prozess Anfragen annimmt. `/readyz` fragt ChurchTools je Mandant höchstens alle 60 Sekunden mit `GET /api/whoami` und antwortet mit 200 oder 503, ohne Einzelheiten. `/metrics` antwortet auf einem eigenen Port nur, wenn der Betreiber ihn setzt, im Textformat von Prometheus mit eigenem Code wie beim Runner, ohne Inhalte. Der Reverse-Proxy des Bundles gibt nur den Pfad für MCP, `/healthz` und `/.well-known/oauth-protected-resource` frei, so dass im Bundle niemand von aussen über `/readyz` Anfragen an ChurchTools auslöst (T20). Wer ohne das Bundle an eine andere Adresse als Loopback bindet, schützt `/readyz` selbst; in jedem Fall begrenzt der Cache die Anfragen auf eine je Minute und Mandant.
- **Zustand über eine Anfrage hinaus (ergänzt ADR 0051):** Vier weitere benannte Ausnahmen im Arbeitsspeicher, zusätzlich zum Pool der Verbindungen und zum Zähler der Drosselung:
  - die Zähler des Rate-Limits je Prinzipal und je Adresse eines Clients und der Zähler der Zeilen vom Typ `auth` je Minute im Prozess;
  - die Zähler für die Metriken des Servers, auch ohne gesetzten Port für `/metrics`, nur Zahlen je Art eines Ereignisses;
  - das Ergebnis von `/readyz` je Mandant für 60 Sekunden, nur bereit oder nicht bereit;
  - im OAuth-Modus die öffentlichen Schlüssel des Anmeldediensts je Aussteller ([ADR 0074](0074-bearer-tokens-und-oauth-pruefung.md)).

  Keine trägt Inhalte aus ChurchTools oder Zugangsdaten, ein Neustart setzt sie zurück, und zwei Prozesse teilen nichts. Zwei weichen von ADR 0051 ab, mit Grund: Die Zähler je Adresse eines Clients gehören zu keinem Mandanten, weil vor der Anmeldung keiner feststeht; sie tragen nur die Adresse und eine Zahl. Das Ergebnis von `/readyz` gilt je Mandant, ohne Akteur und Route, weil es nur bereit oder nicht bereit trägt und für jeden Akteur gleich ist. Die Schlüssel gelten je Aussteller.

- **Audit über HTTP:** wie über stdio zuerst in die Audit-Datei und danach als Kopie über den Logger auf stderr, ohne Kennungen in der Kopie ([ADR 0028](0028-audit-ereignis-und-datei-sink.md)). Die Logzeile eines Prompts nennt über HTTP den Mandanten ([ADR 0065](0065-mcp-prompts-als-feste-vorlagen.md)).
- **Synchrone Zugriffe auf Dateien:** Audit-Datei, `QuotaStore` und Sperrdateien schreiben weiter synchron. Das hält heute drei Regeln einfach: die Reihenfolge der Kette im Audit, die Zeile auf der Platte vor dem Ergebnis eines Tools mit `sensitivity: special` und das Zählen des Lesebudgets. Über HTTP laufen Anfragen mehrerer Prinzipale im selben Prozess. Eine Messung mit 20 Clients parallel und ein Test mit zwei Prinzipalen gleichzeitig zeigen, ob das reicht. Blockiert die Event-Loop dabei im 99. Perzentil länger als 100 Millisekunden, kommen die betroffenen Wege auf asynchrone Zugriffe, ohne eine der drei Regeln aufzugeben. Das Ergebnis steht unter «Umsetzung».

## Konsequenzen

- Clients mit älterer Protokollversion lesen über HTTP wie alle anderen, schreiben aber nur über die Freigabe-Warteschlange oder, mit ausdrücklich gesetztem `echo-allowed`, über das Echo. Über die Warteschlange braucht eine Person, die schreiben will, einen Betreiber, der mit `ecclium queue approve` freigibt.
- Ein Neustart des Servers beendet offene Rückfragen. Der Client sieht einen Fehler, die Person stellt die Aufgabe neu.
- Der freie Kern skaliert über HTTP nicht über mehrere Prozesse. Wer das braucht, ersetzt die drei Zustands-Ports und den Schlüssel, im gehosteten Betrieb mit dem Pro-Modul.
- Ein Client, der auf Änderungen der Liste wartet, erhält einen Fehler statt eines Stroms. Neue Tools gibt es ohnehin nur nach einem Neustart.
- Hinter einem Reverse-Proxy muss `ECCLIUM_TRUSTED_PROXIES` stimmen, sonst zählt das Rate-Limit nur die Adresse des Proxys. Das Bundle setzt sie, eine eigene Installation muss es selbst tun, und `ecclium doctor` meldet eine Bindung an eine andere Adresse als Loopback ohne vertrauten Proxy als Befund.
- Restrisiken:
  - Clients ausserhalb eines Browsers senden oft kein `Origin`. Gegen DNS-Rebinding hilft dann die Prüfung von `Host`; ein Client mit gültigem Token und gefälschtem `Host` ist kein Angriff über einen Browser.
  - Die Zähler des Rate-Limits und der Cache von `/readyz` beginnen nach einem Neustart bei null.
  - Bis zur Messung ist offen, wie sich synchrone Zugriffe unter Last verhalten.
  - Die Obergrenze je Akteur verhindert nicht, dass fünf Akteure mit je 20 offenen Plänen die 100 des Prozesses füllen und die übrigen für bis zu 600 Sekunden sperren. Dafür braucht es fünf angemeldete Prinzipale mit dem Scope `write`.
  - Ob die Kopfzeile der Protokollversion bei allen Clients zur Version im Körper passt, ist für ChatGPT, Claude Code und `initialize` von claude.ai belegt, für die übrigen Anfragen von claude.ai erst mit dem Client-Test. Bis dahin kann die Regel dort einen Client abweisen, der sonst funktionieren würde.

## Umsetzung

- **SDK-Paar, 17.11.2026:** `@modelcontextprotocol/server` 2.4.0 nach der Prüfung des gebündelten Codes ([ADR 0059](0059-gebuendelter-code-im-mcp-sdk.md), Umsetzung), dazu `@modelcontextprotocol/hono` 2.0.2 und `hono` 4.13.18 im Paket `server`, je genau gepinnt.
- **Keine Brücke aus `@hono/node-server`, 17.11.2026 entschieden:** Das Paket ersetzt in der Voreinstellung die globalen `Request` und `Response` des Prozesses und schreibt mit `console.info` oder `console.error` an der Logger vorbei, wenn das Schreiben einer Antwort als Strom scheitert, etwa wenn ein Client abbricht; die zweite Stelle lässt sich nicht abstellen. Eine eigene kleine Brücke auf `node:http` im Ort `ingress` folgt mit den Zeitlimits und der Bindung. Der Adapter bleibt: Seine Prüfungen von `Host` und `Origin` sind die erste Schicht vor den genauen Regeln dieses ADR.
- **Ort `ingress`, 18.11.2026:** `packages/server/src/http/` steht als Ort `ingress` in `tests/architecture/boundaries.json`. Nur er importiert `hono` und den Adapter, ESLint meldet es sonst als `[arch:ingress]` und dependency-cruiser als `hono-only-in-ingress`, je mit Fällen, die rot werden. Der Unterpfad `./http` des Pakets `server` gibt nur `createHttpApp` und ihre Typen heraus.
- **Anwendung, 18.11.2026:** `createHttpApp` lässt sich nur mit einer Prüfung der Anmeldung bauen, ohne Voreinstellung. Jede Anfrage läuft durch die Prüfung von `Host` und `Origin` des Adapters, die Anmeldung vor dem Lesen des Körpers (401), die Prüfung des Typs (415), den Leser des SDK mit 1 MiB (413), `JSON.parse` (400 mit -32700), die Tiefe von höchstens 64 Ebenen (400) und die Abweisung von `subscriptions/listen` mit -32601, auch in einer Liste. Erst dann sieht der Handler des SDK die Anfrage, mit dem gelesenen Körper als `parsedBody`, so dass die Prüfungen und das SDK dieselbe Nachricht sehen. Andere Pfade enden mit 404. Eine angegebene Länge über 1 MiB endet mit 413, bevor etwas gelesen wird. Eine Identität aus der Prüfung der Anmeldung, die nicht die Form hat, die der Mount nimmt, zählt als Abweisung (401). Die Antworten des Adapters auf `Host` und `Origin` nennen den Wert, den der Client sandte; der Ort setzt feste Sätze an ihre Stelle, mit den Ereignissen `http_host_refused` und `http_origin_refused`.
- **Identität je Anfrage:** Der Mount nimmt über HTTP statt der festen Identität des Starts eine Funktion, die die geprüfte Identität einer Anfrage aus dem Kontext der Fabrik liest. Sie kommt dort im `authInfo` des SDK an, dem Weg, den das SDK für Server mit mehreren Prinzipalen vorsieht; das Token selbst bekommt das SDK nie. Ein Test hält zwei Prinzipale in zwei Mandanten in einem Prozess auseinander, in beiden Ären.
- **`responseMode: 'auto'` statt `'json'`:** `'json'` schreibt bei jedem Bau eines Handlers eine feste Warnung mit `console.warn` an der Logger vorbei. Der Mount sendet vor einem Ergebnis nichts, und das SDK wechselt nur dann auf einen Strom, wenn vor dem Ergebnis eine andere Nachricht geht (`PerRequestHTTPServerTransport`, `mcp-oHn3ureC.mjs:176-210` in 2.4.0), also antwortet auch `'auto'` in der Ära 2026 mit JSON. Die Tests verlangen JSON für jede Antwort, nach der Umwandlung eines Stroms mit einer Nachricht. Den Weg der Ära 2025 beantwortet das SDK als Strom mit einer Nachricht, den der Ort `ingress` als JSON weitergibt.
- **Frist für den `TenantResolver`:** zehn Sekunden über stdio und HTTP, dann `upstream`; die Pipeline nimmt dafür das Feld `resolverLate`. Die Logzeile eines Prompts nennt über HTTP den Mandanten, über einen Logger, an den die Wurzel der Komposition ihn bindet.
- Restrisiko: Fehler des SDK nach der Anmeldung wiederholen, was der angemeldete Client selbst sandte, etwa eine Kopfzeile, die nicht passt, eine Version oder bei einem kaputten `initialize` der Ära 2025 die Pfade seiner Eingabe. Sie gehen nur an diesen Client zurück. Das SDK meldet solche Fehler auch an `onerror`, was je eine Zeile `mcp_http_error` auf der Stufe `error` schreibt; die Grenze je Prinzipal bringt das Rate-Limit.
- **Host und Origin genau, 19.11.2026:** Nach der Prüfung des Adapters, die nur Namen kennt und die Kopfzeile wie ein Parser für URLs liest, folgt eine eigene Prüfung (`hosts.ts`). Die Einträge folgen einer eigenen Grammatik und nur in ihrer kanonischen Form: ein DNS-Name, der nicht auf eine Zahl endet, eine IPv4-Adresse ohne führende Nullen, eine IPv6-Adresse in Klammern, wie ein Parser für URLs sie schreibt, und ein Port von 1 bis 65535 ohne führende Null. Die Kopfzeilen vergleicht der Ort als Text und liest sie nie wie eine URL, so passt `127.1`, ein Benutzer vor `@` oder zwei Werte mit Komma zu keinem Eintrag. Ein Eintrag ohne Port erlaubt nur den Namen ohne Port; wer einen Port braucht, schreibt ihn in den Eintrag (entschieden am 19.11.2026). Ein `Origin` muss `https://` und die Schreibweise eines Eintrags sein, für die Namen von Loopback auch `http://`, in Kleinbuchstaben und ohne Pfad. Ohne Liste gelten die Namen von Loopback mit dem Port, auf dem die Verbindung ankam; die Brücke gibt ihn je Anfrage mit, und ohne ihn passt kein `Host`. Eine leere Liste oder ein Eintrag anderer Form beendet den Bau. `parseAllowedHosts` liest die Liste mit Komma, so wie `ecclium serve-http` die Variable lesen wird.
- **Eigene Brücke auf `node:http`, 19.11.2026:** `listenHttp` baut Anwendung und Server aus denselben Optionen, damit eine Liste der Hosts für die Prüfung und für die Bindung gilt. Die URL einer Anfrage ist eine feste Basis mit dem Pfad des Clients, nie mit seinem `Host`; ein Ziel in anderer Form, etwa die absolute Form eines Proxys oder `*`, endet mit 400. Die Kopfzeilen kommen aus `rawHeaders`, zwei gleichnamige erreichen die Prüfungen verbunden. Der Körper ist ein Strom ohne Puffer, den erst die Anwendung liest; so bleibt die Abweisung ohne Anmeldung auch über einen Socket ohne Lesen des Körpers, und nach 1 MiB und einem Stück endet der Strom mit einem Fehler. Was nach der Antwort vom Körper übrig ist, liest die Brücke weg, höchstens 1 MiB mehr, sonst beendet sie die Verbindung; ein sofortiges Schliessen könnte die Antwort an einen Reset verlieren, solange der Client noch sendet. Die Antwort geht in einem Stück mit `Content-Length` hinaus. Geht der Client, bricht das Signal der Anfrage ab, und ein Aufruf endet mit `network`. Was Node.js nicht lesen kann, beantwortet die Brücke wie Node.js selbst (400, 408, 431) und schreibt das feste Ereignis `http_client_error`; ein Abbruch durch den Client schreibt keine Zeile. HTTP/1.1 ohne `Host` beantwortet Node.js selbst mit 400, ohne Zeile.
- **Zeitlimits:** Kopfzeilen 10 Sekunden und höchstens 16 KiB, die ganze Anfrage 120 Sekunden, eine ruhende Verbindung 5 Sekunden, und Node.js prüft die Fristen jede Sekunde statt alle 30. Die 120 Sekunden decken das Empfangen der Anfrage samt Körper, nicht die Arbeit danach; die begrenzen die Frist des Resolvers (zehn Sekunden) und die Fristen des ausgehenden Wegs (30 Sekunden je Anfrage an ChurchTools). Zehn Sekunden für Kopfzeilen reichen auch einem langsamen Client und schliessen eine Verbindung, die Kopfzeilen tröpfeln lässt, früh; 120 Sekunden tragen 1 MiB auch über eine langsame Leitung.
- **Bindung:** voreingestellt `127.0.0.1`, nur IP-Adressen. Jede andere Adresse als `127.0.0.1` und `::1` verlangt eine Liste der Hosts, sonst wirft `listenHttp` `HttpBindError`, den `ecclium serve-http` auf 78 abbilden wird. `close` nimmt nichts mehr an, schliesst ruhende Verbindungen sofort und alle übrigen nach höchstens zehn Sekunden.
- **Kein CORS:** Die Anwendung entfernt jede Kopfzeile `Access-Control-*` aus jeder Antwort, weil der Server keine Seite ausliefert und der Helfer des SDK für die Metadaten einer geschützten Ressource `Access-Control-Allow-Origin: *` setzt. `OPTIONS` bleibt hinter der Anmeldung: ohne sie 401, mit ihr 405 vom SDK (entschieden am 19.11.2026). So gibt es vor der Anmeldung weiter nur 401, 403 und 404, und eine Vorabfrage eines Browsers trägt nie ein Token.
- **Kopfzeile der Protokollversion:** Der Ort gibt `MCP-Protocol-Version` weiter, wie der Client sie sandte; eine Abweichung vom Körper beantwortet das SDK mit 400. Die Ersatzregel bleibt vorbereitet.
- **Regel `[arch:listen]`:** Nur der Ort `ingress` importiert `createServer` aus `node:http`, kein anderer Name dieses Moduls, auch keinen Typ, keinen Standardimport und kein `import *`; `fetch`, `https`, `net` und undici bleiben dort `[arch:network]`. dependency-cruiser sieht keine Namen und erlaubt dem Ort mit der Regel `ingress-listens-only` genau `http`.
- **Test auf `127.0.0.1`:** `tests/http-listen.test.mts` bindet als einzige Testdatei, mit einem Port vom System, kurzen Fristen und einem rohen Socket als Client, weil `fetch` weder einen gewählten `Host`, zwei `Host`, die absolute Form noch langsame Kopfzeilen senden kann.
- Noch offen: das Lesen von `ECCLIUM_ALLOWED_HOSTS` mit `ecclium serve-http`. Mit einer Liste gelten die Namen von Loopback nicht mehr von selbst; eine Prüfung der Gesundheit im Container über `127.0.0.1` braucht dann einen Eintrag oder einen anderen Weg. Die URL einer Anfrage nennt nie den öffentlichen Namen; die Metadaten nach RFC 9728 brauchen deshalb die öffentliche Adresse aus der Konfiguration.
