# ADR 0074: Statische Bearer-Tokens und Prüfung im OAuth-Modus: Format, Ablauf, Rotation, Widerruf, Subjekt im Audit, Prüfliste für JWT und zugesagter Weg, ergänzt ADR 0028, ADR 0037, ADR 0056 und ADR 0063

- Status: Vorgeschlagen
- Datum: 16.11.2026
- Fällt vor: Phase 7

## Kontext

[ADR 0037](0037-anmeldung-am-server.md) legt fest, wie sich Clients über HTTP am Server anmelden: mit statischen Bearer-Tokens oder im OAuth-Modus mit JWT-Zugriffstokens eines Anmeldediensts, den der Betreiber stellt. Es lässt offen, wie die Tokens aussehen, wo der Server sie hält und wie Ablauf und Rotation gehen, und nennt die Prüfung im OAuth-Modus nur in groben Zügen. Am 10.10.2026 ist entschieden: Ein statisches Token läuft in der Voreinstellung nach 180 Tagen ab, und eine Rotation überlappt sieben Tage, umgesetzt mit einem ADR, das ADR 0037 ergänzt, vor dem Code für HTTP (`docs/STATUS.md`, Grundsatzentscheid 12; Threat Model T3).

Weitere Bedingungen:

- **Prinzipal:** Über HTTP ist der Prinzipal das Subjekt des Tokens. Es wird `actor.id` im Audit und bestimmt die Pseudonyme der Stufe `strict` ([ADR 0026](0026-klassifizierte-ausgabeschemas.md), [ADR 0069](0069-stufe-strict.md)). Ein Anmeldedienst kann als Subjekt eine E-Mail-Adresse setzen. Das Schema des Audits nimmt als Kennung eines Akteurs nur `^[a-z][a-z0-9_-]{0,31}(?::[a-z0-9_-]{1,64})?$` an (`schemas/audit-event.v1.json`). Über stdio ist das Subjekt eine neutrale Bezeichnung nach `^[a-z][a-z0-9-]{0,31}$` ([ADR 0055](0055-konfiguration-identitaet.md)).
- **Speicher:** Der Runner-Container-Vertrag bindet `/config` nur lesbar ein ([ADR 0036](0036-runner-container-vertrag.md)), und das Bundle für das Self-Hosting tut das für den Server ebenso, damit ein übernommener Server seine Konfiguration nicht ändern kann. Der `QuotaStore` kennt nur Zähler je Tag (`increment` und `read`), löscht gewöhnliche Zähler am nächsten Tag und hält nur die Zähler der Freigaben 15 und die der Läufe 32 Tage ([ADR 0063](0063-quotastore-als-datei.md), [ADR 0029](0029-write-guard.md), [ADR 0034](0034-zeitplan-semantik.md)).
- **Ein Weg nach draussen:** Verbindungen öffnet nur der Ort `egress` ([ADR 0056](0056-ausgehender-weg.md)). Metadaten und Schlüssel eines Anmeldediensts kommen deshalb über den `HttpTransport`, mit Issuer und `jwks_uri` auf der Positivliste ([ADR 0009](0009-positivliste-ausgehend.md)).
- **jose** 6.2.17 vom 09.11.2026 steht unter MIT, ohne Abhängigkeiten und mit Herkunftsnachweis (Registry von npm, geprüft am 16.11.2026). Seine Funktion für entfernte Schlüssel holt sie selbst mit `fetch`, eine lokale Menge von Schlüsseln nimmt sie aus dem Speicher.
- Ein Fehlversuch soll im Audit stehen, ohne dass das Audit Inhalte oder Zugangsdaten trägt ([ADR 0028](0028-audit-ereignis-und-datei-sink.md)).
- **Clients:** Claude beginnt jede Anmeldung mit einer Anfrage ohne Token, auf die der Server mit 401 antworten muss, und erneuert ein Token nach einer Antwort 401 (Claude Docs, «Authentication for connectors», abgerufen am 16.11.2026).
- **Anmeldedienst:** Für den Test mit den Clients ist Keycloak vorgesehen, der Dienst mit den meisten der Bedingungen aus ADR 0037 in seiner Doku. Keycloak 26.8 führt Client ID Metadata Documents und Resource Indicators (RFC 8707) als experimentelle Funktionen, die laut Hersteller mit späteren Versionen brechen können. Ohne Resource Indicators setzt es `aud` über eine feste Zuordnung (Audience-Mapper) und übergeht `resource`. `typ: at+jwt` ist dort eine Einstellung je Client, sonst steht `JWT` im Kopf (Keycloak, «Integrating with Model Context Protocol (MCP)», und Quelltext 26.8.2, abgerufen am 16.11.2026).

## Optionen

1. **Subjekt so, wie der Anmeldedienst es setzt, nur in neutraler Form:** Ein Subjekt, das nicht passt, weist der Server ab. Die Person hinter einem Eintrag im Audit findet der Betreiber direkt in seinem Anmeldedienst. Dienste, die eine E-Mail-Adresse als Subjekt setzen, muss der Betreiber umstellen.
2. **Subjekt nur als Hash mit einem Schlüssel des Servers:** Jeder Anmeldedienst geht, aber die Zuordnung zu einer Person braucht einen eigenen Befehl, und es gibt ein Geheimnis mehr, das gesichert werden muss.

Für den Tag der letzten Verwendung: in der Datei der Tokens unter `/config`, die im Container nur lesbar ist, oder im Zustandsordner.

## Entscheid

Gewählt ist die erste Option, dazu gilt:

- **Format:** `ecclium_mcp_`, dann 43 Zeichen Base62 aus 32 Bytes eines sicheren Zufallsgenerators (256 Bit), dann 6 Zeichen Base62 mit der Prüfsumme CRC32 über die 43 Zeichen. Der Server prüft Präfix, Länge und Prüfsumme, bevor er nachschlägt. Eine Regel in `.gitleaks.toml` erkennt das Muster, mit einem Beispiel, das sie findet, und einem, das sie nicht findet. Dasselbe Muster wird für die Push Protection von GitHub angemeldet, sobald das Paket öffentlich ist.
- **Datei der Tokens:** `ECCLIUM_HTTP_TOKENS_FILE` nennt eine YAML-Datei unter `/config`, nur lesbar für den Server. Je Eintrag: Name, SHA-256 des ganzen Tokens, Scopes (`read` oder `read` und `write`), `createdAt` und `expiresAt` als Tag. Das Token selbst steht nirgends, es erscheint nur einmal in der Ausgabe von `ecclium token create`. Der Server liest die Datei neu, wenn sie sich ändert, ohne Neustart. Er vergleicht den Hash in konstanter Zeit.
- **Name eines Tokens:** neutral nach `^[a-z][a-z0-9-]{0,31}$`, etwa `claude-code-buero`. Die Doku rät von Namen von Personen ab.
- **Befehle:** `ecclium token create <Name>` mit den Scopes und einer Dauer von höchstens 365 Tagen, voreingestellt 180. `ecclium token rotate <Name>` erzeugt ein neues Token und setzt den Ablauf des alten auf höchstens sieben Tage; in dieser Zeit stehen zwei Einträge mit demselben Namen in der Datei. `ecclium token revoke <Name>` entfernt alle Einträge des Namens; ab der nächsten Anfrage ist ein solches Token für den Server unbekannt. `ecclium token list` zeigt Name, Scopes, Tage und letzte Verwendung, nie einen Hash. Die Befehle laufen dort, wo `config/` schreibbar ist, im Bundle in einem eigenen Dienst für die Befehle der Kommandozeile.
- **Letzte Verwendung (ergänzt ADR 0063):** Der Tag der letzten Anmeldung je Name liegt im Zustandsordner, im `QuotaStore`, ein Tag je Name und Mandant, höchstens einmal am Tag geschrieben. Dafür bekommt der Port eine Methode, die je Schlüssel einen Tag festhält und liest, weil seine Zähler je Tag das nicht ausdrücken; ein Ersatz aus einem Plugin muss sie ebenfalls können. Ein Eintrag bleibt höchstens 365 Tage nach seinem Tag, so lange, wie ein Token höchstens gilt. Das ist kein neuer Port und keine neue Ausnahme der Persistenz: nur Tage je Name, keine Inhalte. `ecclium doctor` warnt 30 Tage vor dem Ablauf eines Tokens und nennt Tokens, die seit 90 Tagen nicht benutzt wurden.
- **Scopes:** `read` erlaubt jedes Lese-Tool, das der Server anbietet. Ein Tool mit `capability: write` braucht `write`. Ohne `write` zeigt `tools/list` keine Schreib-Tools, und ein Aufruf eines solchen endet mit 403, `insufficient_scope` und `scope="write"` in `WWW-Authenticate` ([ADR 0037](0037-anmeldung-am-server.md)). Mit `ECCLIUM_READ_ONLY=true` gibt es keine Schreib-Tools, gleich welche Scopes ein Token trägt. Im OAuth-Modus entscheidet der Anmeldedienst, welche Person welchen Scope erhält; Ecclium prüft nur, was im Token steht. Die Doku verlangt deshalb: keine Selbstregistrierung, Konten von Hand und `write` nur für eine eigene Rolle. Der Test mit den Clients prüft, dass eine Person ohne diese Rolle kein Token mit `write` erhält.
- **Akteur im Audit:** Ein Bearer-Token ergibt den Akteur `bearer:<Name>`, ein JWT den Akteur `oauth:<Subjekt>`, beide mit der Art `user`. So ergeben ein Token und ein Subjekt mit gleichem Text nie denselben Akteur. Ein Subjekt muss `^[a-z0-9_-]{1,64}$` erfüllen, etwa eine UUID in Kleinbuchstaben oder eine Zahl. Ein Subjekt mit `@`, Punkt, Leerzeichen oder Grossbuchstaben weist der Server mit 401 ab und schreibt eine Logzeile ohne den Wert. Die Doku sagt, wie gängige Anmeldedienste ein solches Subjekt setzen. Pseudonyme folgen dem Akteur wie bisher.
- **Fehlversuche im Audit (ergänzt ADR 0028):** Jede abgewiesene Anmeldung schreibt eine Zeile vom neuen Typ `auth` mit `outcome: denied`, `errorCode: auth` und einem Grund in einem neuen Feld aus einer festen Liste (Form, Prüfsumme, unbekannt, abgelaufen bei einem statischen Token, Signatur, Aussteller, Audience, noch nicht gültig, Algorithmus, Typ, Subjekt). Ein widerrufenes Token ist danach unbekannt. Keine Zeile schreiben zwei Fälle, die bei OAuth zum gewöhnlichen Ablauf gehören: eine Anfrage ganz ohne Token und ein JWT mit gültiger Signatur, richtigem Aussteller und richtiger Audience, das nur abgelaufen ist. Beide erhalten immer 401 mit dem Verweis auf die Metadaten, zählen nicht gegen die Grenze je Adresse ([ADR 0073](0073-betrieb-ueber-http.md)) und stehen nur in den Metriken. Die Zeile nennt den Mandanten des Servers, im freien Kern den einen, den Modus `interactive` und die Art `user`. Ist der Name eines Tokens bekannt, nennt sie den Akteur `bearer:<Name>`, sonst `unauthenticated`. Ein fehlender Scope ist kein Fehlversuch: Die Anmeldung gilt, und der Aufruf steht als abgelehnter `tool_call` des angemeldeten Akteurs im Audit. Sie nennt nie eine IP-Adresse, nie ein Token oder einen Teil davon und nie einen Wert aus einem JWT. Die Adresse kennen nur die Zähler des Rate-Limits im Arbeitsspeicher und das Log des Reverse-Proxys ([ADR 0073](0073-betrieb-ueber-http.md)). Nach dem Rate-Limit je Adresse schreibt der Server keine weitere Zeile, und im ganzen Prozess höchstens 60 Zeilen vom Typ `auth` je Minute; darüber zählt er nur in den Metriken, damit Fehlversuche von vielen Adressen das Audit nicht ohne Grenze wachsen lassen. Der Typ `auth` erweitert die Liste der Typen im Ereignis v1.
- **Beide Wege zugleich:** Ein Server kann statische Tokens und den OAuth-Modus zugleich annehmen, etwa Claude Code mit Token und claude.ai mit OAuth. Das Präfix entscheidet, welcher Weg prüft.
- **Prüfliste im OAuth-Modus**, jeder Punkt mit einem Negativtest:
  - Die Algorithmen stehen in der Konfiguration, voreingestellt `ES256` und `EdDSA`, auf Wunsch `RS256` oder ein anderer asymmetrischer Algorithmus wie `ES384`, nur als ausdrücklicher Eintrag. `alg` im Kopf des Tokens wählt nie den Algorithmus, `none` wird immer abgewiesen.
  - Erwartet wird `typ: at+jwt` (RFC 9068). Setzt der Anmeldedienst `JWT`, muss der Betreiber das ausdrücklich erlauben; dann gilt neben `at+jwt` genau `JWT`, kein anderer und kein fehlender Wert. Was dann noch ein falsches Token abhält, etwa ein ID-Token desselben Diensts, sind `aud` gleich der Adresse des Servers und ein bekannter Scope. Ein Negativtest mit einem solchen Token belegt das.
  - `aud` enthält genau die kanonische Adresse des Servers, ohne Toleranz für einen Pfad. `iss` gleicht dem konfigurierten Aussteller Byte für Byte.
  - `exp` und `nbf` werden geprüft, mit höchstens 60 Sekunden Abweichung der Uhren.
  - Beim Start liest der Server die Metadaten des Anmeldediensts und daraus `jwks_uri` und pinnt sie. Die Schlüssel hält er höchstens eine Stunde und holt sie bei einer unbekannten `kid` höchstens alle fünf Minuten neu, damit niemand ihn zu Abrufen zwingen kann. Gelingt der erste Abruf nicht, endet der Start mit 69. Nimmt der Server beide Wege an, hält ein unerreichbarer Anmeldedienst beim Start damit auch die Clients mit statischem Token draussen; die Anleitung sagt, wie der Server erst nach dem Anmeldedienst startet.
  - Scopes des Anmeldediensts bildet die Konfiguration auf `read` und `write` ab. Ein Token ohne bekannten Scope hat keinen.
- **jose:** Laufzeitabhängigkeit im Kern, exakt gepinnt, nur zur Prüfung mit einer lokalen Menge von Schlüsseln. Metadaten und Schlüssel holt der `HttpTransport` mit dem neuen Zweck `oauth` neben `model` und `ping` (ergänzt ADR 0056). Die Funktion von jose für entfernte Schlüssel benutzt Ecclium nie, weil sie am einzigen Weg nach draussen vorbeiginge.
- **Metadaten nach RFC 9728:** unter `/.well-known/oauth-protected-resource` mit der kanonischen Adresse, dem Aussteller und den Scopes. Eine Antwort 401 im OAuth-Modus nennt sie in `WWW-Authenticate` mit `resource_metadata`.
- **Kein Weiterreichen:** Kein Token eines Clients geht je an ChurchTools ([ADR 0023](0023-kein-token-passthrough.md)).
- **Zugesagter Weg (ergänzt ADR 0037):** Zugesagt und in der Abnahme verlangt ist der Weg mit vorab registrierten Clients: claude.ai mit einer eigenen OAuth-Anwendung und ChatGPT mit hinterlegten Zugangsdaten. Client ID Metadata Documents prüft der Test mit den Clients ebenfalls; das Ergebnis steht mit Dienst, Version und Datum als Befund in `docs/STATUS.md`, und die Doku nennt diesen Weg experimentell, solange der genannte Anmeldedienst ihn so führt. «Mit dem Client-Test bestanden» aus ADR 0037 heisst damit: auf dem zugesagten Weg, mit Dienst, Version und Datum des Laufs. Scheitert ein Test an einem Client und nicht an Ecclium, steht das als Befund in der Doku und hält das Release nicht auf.
- **Audience (ergänzt ADR 0037):** Die Audience ist genau die kanonische Adresse des Servers, gleich ob der Anmeldedienst sie nach RFC 8707 aus dem Parameter `resource` setzt oder aus einer festen Zuordnung. Ecclium prüft `aud` in beiden Fällen gleich. Auf dem zugesagten Weg kommt sie aus der festen Zuordnung, ohne experimentelle Funktion des Diensts.
- **Doku zum Anmeldedienst:** Die freie Doku beschreibt die Schritte für den genannten Dienst von Hand, mit Platzhaltern, getrennt nach zugesagtem und experimentellem Weg. Eine fertige Konfiguration des Diensts, etwa eine Datei für einen Realm, liegt nicht im Repository; ein vorkonfigurierter Dienst bleibt Sache des Zusatzmoduls ([ADR 0037](0037-anmeldung-am-server.md)).

## Konsequenzen

- Ein Token in einem öffentlichen Repository erkennen Scanner ohne Zusammenhang am Präfix, nach der Anmeldung des Musters auch die Push Protection von GitHub.
- Ein Widerruf wirkt ab der nächsten Anfrage. Eine Rotation lässt dem Client sieben Tage für das neue Token.
- Ein Anmeldedienst, der eine E-Mail-Adresse als Subjekt setzt, funktioniert erst, wenn der Betreiber ihn umstellt. Dafür steht im Audit nie eine E-Mail-Adresse, und es braucht kein weiteres Geheimnis.
- Der Zustandsordner trägt neu den Tag der letzten Verwendung je Name eines Tokens. `docs/privacy.md` nennt das.
- Die Abnahme hängt nicht an experimentellen Funktionen eines fremden Diensts. Dafür ist die Audience auf dem zugesagten Weg eine feste Zuordnung im Anmeldedienst statt eines Parameters nach RFC 8707, mit demselben Zweck: Ein Token gilt nur für diesen Server.
- Wer claude.ai oder ChatGPT anbinden will, betreibt neben Ecclium einen zweiten öffentlichen Dienst. Die Doku zeigt deshalb stdio und statische Tokens zuerst und OAuth als Weg für Betreiber mit eigener IT.
- Wer das Schema des Audits genau prüft, muss den Typ `auth` und sein Feld für den Grund annehmen. Vor v0.1.0 gibt es noch keine Leser ausser Ecclium selbst.
- Restrisiken:
  - Ein statisches Token steht beim Client im Klartext, etwa in der Konfiguration von Claude Code. Wer es liest, benutzt den Server bis zum Ablauf oder Widerruf (T3).
  - Ein Name in der Form `max-mustermann` passt auf das Muster, wie beim Subjekt über stdio ([ADR 0055](0055-konfiguration-identitaet.md)).
  - Nach einem Widerruf eines Schlüssels beim Anmeldedienst nimmt der Server Tokens mit diesem Schlüssel noch bis zu einer Stunde an.
  - Ein Subjekt ist nur so neutral, wie der Anmeldedienst es vergibt; das Muster schliesst eine Kennung, die selbst einen Namen trägt, nicht aus.
  - Liegen die Fehlversuche über der Grenze von 60 Zeilen je Minute, stehen sie nur noch als Zahl in den Metriken, nicht im Audit.
  - Gibt ein Anmeldedienst jeder Person `write`, darf jede Person schreiben, was Ecclium erlaubt. Das prüft Ecclium nicht, nur die Einrichtung des Diensts.
  - Mit `JWT` statt `at+jwt` hängt die Trennung von Zugriffs- und ID-Tokens an `aud` und Scope.
  - Der Weg über Client ID Metadata Documents hängt am experimentellen Stand im genannten Dienst und kann mit einer neuen Version brechen, ohne dass sich an Ecclium etwas ändert.
