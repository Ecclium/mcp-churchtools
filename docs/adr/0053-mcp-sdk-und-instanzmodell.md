# ADR 0053: MCP-SDK v2, eine Server-Instanz pro Verbindung und Rückfragen

- Status: Vorgeschlagen
- Datum: 11.10.2026
- Fällt vor: Phase 1

## Kontext

ADR 0018 legt fest, dass Ecclium MCP in der Version 2026-07-28 über das SDK in Version 2 spricht, und sagt: «Für jede Anfrage entsteht eine Server-Instanz.» Offen liess es, wie das SDK den Betrieb ohne Sitzung einstellt, und die Belege zu `input_required` und Sampling. Beides ist am 11.10.2026 an `@modelcontextprotocol/server` 2.3.1 geprüft: am Paket, an seinen Typdefinitionen, am Quelltext in seinen Source Maps und am Repository des SDK beim Tag v2.3.1, dazu an der Spezifikation 2026-07-28. Die Befunde mit ihren Fundstellen stehen in [`docs/research/mcp-sdk-und-elicitation.md`](../research/mcp-sdk-und-elicitation.md). Für diesen Entscheid zählt:

- **Einstieg über stdio:** Zur Protokollversion 2026-07-28 führt über stdio nur `serveStdio` aus `@modelcontextprotocol/server/stdio`. Es ordnet die erste Nachricht einer Verbindung einer Ära zu und bindet die Instanz, die es dafür erzeugt, an die ganze Verbindung. Die Funktionen, die eine Instanz auf die Ära 2026 einstellen, exportiert das SDK nicht. Ein von Hand verbundener Transport spricht nur die Ära 2025.
- **Instanz pro Anfrage:** Über stdio geht das nicht. Eine verbundene Instanz lehnt eine zweite Verbindung ab, und das SDK schreibt dazu: «Use a separate Server instance per connection». Eine Instanz pro Anfrage gibt es nur über HTTP mit `createMcpHandler`.
- **Ältere Clients:** Clients mit einer Protokollversion bis 2025-11-25 bedient `serveStdio` ohne weitere Einstellung. Gibt ein Handler bei ihnen `input_required` zurück, schickt ein Shim des SDK eine echte Anfrage `elicitation/create` an den Client und ruft den Handler mit der Antwort erneut auf. Angenommenen Inhalt prüft der Shim nicht gegen das Schema. Hat der Client keine Elicitation deklariert, liefert der Shim ein Ergebnis mit `isError`.
- **Rückfragen (`input_required`):** Die Spezifikation behandelt `requestState` als vom Angreifer kontrolliert. Der Server muss ihn schützen, sobald er Logik beeinflusst, und darf nur nach Capabilities fragen, die der Client deklariert hat (Seite «Multi Round-Trip Requests», Abschnitt «Server Requirements», Anforderungen 4, 7 und 8). Das SDK bietet dafür einen Codec, der den `requestState` mit HMAC-SHA256 signiert, aber nicht verschlüsselt, mit einer Frist von zehn Minuten in der Voreinstellung. Seine Bindung (`bind`) sieht nur den Kontext der Anfrage, also die Methode und eine Anmeldung über HTTP, nicht die Parameter.
- **Sampling** ist seit 2026-07-28 veraltet (SEP-2577) und wird frühestens mit der ersten Revision ab dem 28.07.2027 entfernt. Die Spezifikation sagt dazu: «New implementations SHOULD NOT adopt it.» Im SDK sind die Typen als veraltet markiert, und die Methoden für Sampling werfen bei einer Anfrage der Ära 2026.
- **Lizenz:** Bis 2.2.0 standen Server und Kernpaket unter MIT, ab 2.3.0 unter Apache-2.0. Die Datei `LICENSE` beschreibt einen laufenden Wechsel, mit dem Text von Apache-2.0, dem Text von MIT für noch nicht umlizenzierte Beiträge und einem Hinweis auf CC-BY-4.0. ADR 0018 nennt noch MIT.
- **Gebündelter Code:** Das Serverpaket bündelt Code von acht anderen Paketen in seine eigenen Dateien, darunter `fast-uri` 3.1.0. Dafür sind neun Schwachstellen bekannt, acht davon «hoch», behoben in den Versionen 3.1.1 bis 3.1.8. Was gebündelt ist, steht nicht im Lockfile. Die Prüfung der Lizenzen, `deps-review`, Renovate und ein Override in pnpm sehen es nicht.
- **Kein Haken vor dem Handler:** Ein unbekanntes Tool und ein Fehler bei der Prüfung der Eingabe enden als JSON-RPC-Fehler -32602 oder als Ergebnis mit `isError`, bevor ein Handler von Ecclium läuft. Sie erreichen auch `onerror` nicht.

ADR 0018 ist angenommen. Ein angenommener Entscheid ändert sich nur durch ein neues ADR, das ihn ablöst (ADR 0001).

## Optionen

1. **ADR 0018 wörtlich umsetzen:** eine Instanz pro Anfrage auch über stdio. Mit dem SDK geht das nicht, ohne die nicht exportierten Funktionen nachzubauen, und dieser Nachbau wäre eine eigene Umsetzung des Protokolls, die ADR 0018 verworfen hat.
2. **Über stdio bei der Ära 2025 bleiben:** ein von Hand verbundener Transport mit einer Instanz pro Verbindung, ohne `serveStdio`. Dann spräche Ecclium über stdio nicht die Version 2026-07-28, die ADR 0018 festlegt.
3. **`serveStdio` mit einer Instanz pro Verbindung, die keine Daten einer Anfrage hält,** und über HTTP eine Instanz pro Anfrage.

## Entscheid

Gewählt ist die dritte Option. Dieses ADR löst ADR 0018 ab. Es übernimmt dessen Entscheid und Konsequenzen, ausser der Instanz pro Anfrage über stdio, und ergänzt, was die Prüfung des SDK zeigt.

**Weiter gilt aus ADR 0018:**

- Ecclium spricht MCP in der Version 2026-07-28 über `@modelcontextprotocol/server`, im Betrieb über HTTP ab Phase 7 zusammen mit `@modelcontextprotocol/hono`. Über HTTP gehen Antworten im JSON-Modus ohne SSE.
- Rückfragen laufen über Multi Round-Trip Requests (`input_required`). Sampling wird nicht benutzt. Alles Zeitgesteuerte läuft im Runner als eigener Prozess.
- **Versionen:** Gepinnt wird die jüngste Version des Serverpakets, die das Mindestalter für neue Versionen erfüllt (ADR 0050). Der Adapter für HTTP kommt mit Phase 7, in einer Version, die zum gepinnten Server passt. Ab dann werden Server und Adapter nur gemeinsam aktualisiert, und das Serverpaket bringt sein Kernpaket `@modelcontextprotocol/core` in genau passender Version mit.
- **stdout im Betrieb über stdio** gehört dem Protokoll, und nur der stdio-Transport des SDK schreibt dorthin. Die Orte im Code stehen in `tests/architecture/boundaries.json`. Der Betrieb über stdio beginnt in `packages/server/src/stdio/` und in `packages/cli/src/stdio/`, und nichts, was von dort aus erreichbar ist, darf auf stdout schreiben. Auf stdout schreiben nur die Meldungen der Kommandozeile in `packages/cli/src/output/`, auf stderr nur der Logger in `packages/core/src/logger/` und dieselben Meldungen. `console` benutzt der Code der Pakete nirgends, `process` nur über einzelne Eigenschaften.
- Das Audit schreibt im Betrieb über stdio über den Logger nach stderr. Im Betrieb über HTTP und im Runner gibt die Kommandozeile dem Audit einen Ausgabestrom mit.
- Die Regel für stdout ist doppelt durchgesetzt, mit dependency-cruiser und ESLint, und ein Test im Betrieb über stdio prüft in Phase 1 zur Laufzeit in einem Kindprozess, dass auf stdout nur Protokollnachrichten erscheinen.
- Was über eine Anfrage hinaus gelten muss, etwa eine offene Bestätigung, liegt nicht im Server, sondern im Kern, mit eigener Frist und eigenem Schutz (ADR 0051).

**Neu:**

- **Einstieg über stdio** ist nur `serveStdio`. Es entsteht eine Instanz pro Verbindung. Die Funktion, die sie erzeugt, ist billig und ohne Nebenwirkung, denn bei einem Client, der zuerst `server/discover` sendet und dann auf `initialize` ausweicht, läuft sie zweimal. Die Instanz hält keine Daten einer Anfrage über diese hinaus (ADR 0051), und der Mandantenkontext entsteht für jeden Aufruf eines Tools neu (ADR 0003).
- **Über HTTP** entsteht in Phase 7 mit `createMcpHandler` eine Instanz pro Anfrage. ADR 0003 nennt «für jede Anfrage eine Server-Instanz». Das heisst ab diesem ADR: über HTTP pro Anfrage, über stdio pro Verbindung, in beiden Fällen ohne Daten einer Anfrage.
- **Ältere Clients über stdio,** vorgeschlagen: `serveStdio` bedient sie mit `legacy: 'serve'` und dem Shim des SDK für `input_required`. Ob das so bleibt, entscheidet sich mit den Läufen des Spikes zu Elicitation, weil der Shim eine echte Anfrage an den Client schickt und dessen Verhalten dabei zählt.
- **Ältere Clients über HTTP** sind offen für Phase 7. `createMcpHandler` bedient sie ohne Sitzung, und eine solche Instanz kennt die Capabilities des Clients nicht. Rückfragen über Elicitation gehen dann nicht. Zur Wahl stehen `stateless` und `reject`. Der Entscheid berührt die Bestätigung von Schreibvorgängen in Phase 5.
- **`requestState`:** Beeinflusst er Logik, ist er mit HMAC signiert und befristet, etwa mit dem Codec des SDK. Er ist an Methode, Mandant und Prinzipal gebunden. Weil `bind` die Parameter nicht sieht, trägt er einen Digest der Parameter, den der Handler beim Wiedereinstieg vergleicht. Er bleibt für den Client lesbar und enthält deshalb keine Geheimnisse und keine Personendaten. Was höchstens einmal gelten darf, etwa eine Bestätigung, verbraucht der Kern selbst, nicht der `requestState`.
- **Antworten auf Rückfragen:** Der Server fragt nur nach Capabilities, die der Client deklariert hat, und verlässt sich nicht darauf, dass eine Antwort kommt. Angenommener Inhalt wird in beiden Ären gegen das Schema geprüft, weil der Shim es nicht tut. Nach einer Ablehnung oder einem Abbruch fragt ein Handler nicht von selbst erneut.
- **Gebündelter Code:** Bis Phase 8, in der die SBOM entsteht, ersetzt eine Liste im Abschnitt «Umsetzung» die Prüfung durch Werkzeuge. Ein Test gleicht sie mit dem installierten Paket ab. Bei jeder neuen Version des SDK prüft eine Person die gebündelten Pakete von Hand auf bekannte Schwachstellen und trägt das Ergebnis mit Datum ein. Eine Version, deren gebündelter Code eine bekannte Schwachstelle hat, kommt nicht in `core` oder `server`, ausser ein eigenes ADR begründet, warum der verwundbare Code dort nicht erreichbar ist.
- **Lizenz:** Server und Kernpaket stehen seit 2.3.0 unter Apache-2.0, die gebündelten Pakete unter MIT, BSD-2-Clause und BSD-3-Clause. Alle stehen auf der Liste der Lizenzen zur Laufzeit.

## Konsequenzen

- Wer den Entscheid zum MCP-SDK lesen will, liest dieses ADR. Mit seiner Annahme trägt ADR 0018 den Status «Abgelöst durch ADR 0053». Verweise auf ADR 0018 in angenommenen ADRs, etwa in ADR 0003, ADR 0020 und ADR 0024, meinen dann die Regeln, die dieses ADR übernimmt. Verweise in Code, Regeln und Dokumentation zeigen mit der Annahme auf dieses ADR.
- Eine Instanz lebt so lange wie die Verbindung, über stdio also so lange wie der Prozess, den der Client startet. Sie hält die verhandelte Ära, die registrierten Tools und offene Anfragen, bei älteren Clients auch deren Capabilities aus `initialize`. Das sind keine Daten einer Anfrage. Legt ein Fehler doch solche Daten in der Instanz ab, trägt er sie in spätere Aufrufe derselben Verbindung. Dagegen stehen die Regel aus ADR 0051 und der Test mit zwei Mandanten (ADR 0003).
- Der `requestState` ist signiert, nicht verschlüsselt. Ein Client kann seinen Inhalt lesen, nicht ändern. Weil der Schlüssel bei jedem Start neu entsteht, gilt nach einem Neustart kein `requestState` von vorher.
- Weil es keinen Haken vor dem Handler gibt, erreichen unbekannte Tools und Fehler bei der Prüfung der Eingabe weder das Audit noch den Logger. Ob ein umhüllender Transport oder ein umhüllendes Schema das in Phase 1 schliesst, entscheidet der Bau des Mounts. Sonst bleibt es ein Restrisiko im Threat Model.
- Die Sperre `[arch:mcp-register]` erfasst auch `registerCapabilities`, `removeRequestHandler` und `removeNotificationHandler`. `RegisteredTool.update` kann den Handler eines Tools austauschen. Der Name ist zu allgemein für eine Regel, die Methoden an ihrem Namen erkennt. Das fängt nur das Review.
- Restrisiko `fast-uri`: In 2.3.1 bündelt das SDK `fast-uri` 3.1.0. ajv nutzt es für `$id` und `$ref`, wenn es ein JSON-Schema übersetzt, also für die Schemas von Tools und Rückfragen. Eine neuere Version des SDK gibt es am 11.10.2026 nicht. Deshalb steht das SDK vorerst nur in `testkit`, für den Spike, der kein Eingabeschema und nur ein festes Schema für die Rückfrage hat. In `core` oder `server` kommt es erst mit einer Version, die `fast-uri` ab 3.1.8 bündelt, oder mit einem eigenen ADR nach der Regel unter «Gebündelter Code».
- Die Liste des gebündelten Codes ist eine Ersatzkontrolle. Der Test erkennt nur Code, den das Werkzeug des Builds mit einem Pfad der Form `node_modules/.pnpm/…` markiert. Diese Markierung ist kein Vertrag und kann mit einem anderen Build verschwinden, dann scheitert der Test an einer leeren Liste. Die Lizenzen der gebündelten Pakete erscheinen im Paket nicht als Hinweise Dritter. Das betrifft die Hinweise, die Phase 8 für das Produktpaket erzeugt.
- Sampling bleibt ungenutzt. Das stützen jetzt die Spezifikation und das SDK.
