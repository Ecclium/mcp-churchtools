# ADR 0053: MCP-SDK v2, eine Server-Instanz pro Verbindung und Rückfragen

- Status: Angenommen am 11.10.2026
- Datum: 11.10.2026
- Fällt vor: Phase 1

## Kontext

ADR 0018 legt fest, dass Ecclium MCP in der Version 2026-07-28 über das SDK in Version 2 spricht, und sagt: «Für jede Anfrage entsteht eine Server-Instanz.» Offen liess es, wie das SDK den Betrieb ohne Sitzung einstellt, und die Belege zu `input_required` und Sampling. Beides ist am 11.10.2026 an `@modelcontextprotocol/server` 2.3.1 geprüft: am Paket, an seinen Typdefinitionen, am Quelltext in seinen Source Maps und am Repository des SDK beim Tag v2.3.1, dazu an der Spezifikation 2026-07-28. Die Befunde mit ihren Fundstellen stehen in [`docs/research/mcp-sdk-und-elicitation.md`](../research/mcp-sdk-und-elicitation.md). Für diesen Entscheid zählt:

- **Einstieg über stdio:** Zur Protokollversion 2026-07-28 führt über stdio nur `serveStdio` aus `@modelcontextprotocol/server/stdio`. Es ordnet die erste Nachricht einer Verbindung einer Ära zu und bindet die Instanz, die es dafür erzeugt, an die ganze Verbindung. Die Funktionen, die eine Instanz auf die Ära 2026 einstellen, exportiert das SDK nicht. Ein von Hand verbundener Transport spricht nur die Ära 2025.
- **Instanz pro Anfrage:** Über stdio geht das nicht. Eine verbundene Instanz lehnt eine zweite Verbindung ab, und das SDK schreibt dazu: «Use a separate Server instance per connection». Eine Instanz pro Anfrage gibt es nur über HTTP mit `createMcpHandler`.
- **Ältere Clients:** Clients mit einer Protokollversion bis 2025-11-25 bedient `serveStdio` ohne weitere Einstellung. Gibt ein Handler bei ihnen `input_required` zurück, schickt ein Shim des SDK eine echte Anfrage `elicitation/create` an den Client und ruft den Handler mit der Antwort erneut auf. Angenommenen Inhalt prüft der Shim nicht gegen das Schema. Hat der Client keine Elicitation deklariert, liefert der Shim ein Ergebnis mit `isError`.
- **Rückfragen (`input_required`):** Die Spezifikation behandelt `requestState` als vom Angreifer kontrolliert. Der Server muss ihn schützen, sobald er Logik beeinflusst, und darf nur nach Capabilities fragen, die der Client deklariert hat (Seite «Multi Round-Trip Requests», Abschnitt «Server Requirements», Anforderungen 4, 7 und 8). Das SDK bietet dafür einen Codec, der den `requestState` mit HMAC-SHA256 signiert, aber nicht verschlüsselt, mit einer Frist von zehn Minuten in der Voreinstellung. Seine Bindung (`bind`) sieht nur den Kontext der Anfrage, also die Methode und eine Anmeldung über HTTP, nicht die Parameter.
- **Sampling** ist seit 2026-07-28 veraltet (SEP-2577) und wird frühestens mit der ersten Revision ab dem 28.07.2027 entfernt. Die Spezifikation sagt dazu: «New implementations SHOULD NOT adopt it.» Im SDK sind die Typen als veraltet markiert, und die Methoden für Sampling werfen bei einer Anfrage der Ära 2026.
- **Lizenz:** Bis 2.2.0 standen Server und Kernpaket unter MIT, ab 2.3.0 unter Apache-2.0. Die Datei `LICENSE` beschreibt einen laufenden Wechsel, mit dem Text von Apache-2.0, dem Text von MIT für noch nicht umlizenzierte Beiträge und einem Hinweis auf CC-BY-4.0. ADR 0018 nennt noch MIT.
- **Gebündelter Code:** Das Serverpaket bündelt Code von acht anderen Paketen in seine eigenen Dateien, darunter `fast-uri` 3.1.0. Dafür sind neun Schwachstellen bekannt, acht davon «hoch», behoben in den Versionen 3.1.1 bis 3.1.8. Was gebündelt ist, steht nicht im Lockfile. Die Prüfung der Lizenzen, `deps-review`, Renovate und ein Override in pnpm sehen es nicht.
- **Kein Haken vor dem Handler:** Ein unbekanntes Tool und ein Fehler bei der Prüfung der Eingabe enden als JSON-RPC-Fehler -32602 oder als Ergebnis mit `isError`, bevor ein Handler von Ecclium läuft. Sie erreichen auch `onerror` nicht.

ADR 0018 ist angenommen. Ein angenommener Entscheid ändert sich nur durch ein neues ADR, das ihn ablöst (ADR 0001).

## Optionen

1. **ADR 0018 wörtlich umsetzen:** eine Instanz pro Anfrage auch über stdio. Mit dem SDK geht das nicht, ohne die nicht exportierten Funktionen nachzubauen, und dieser Nachbau wäre eine eigene Umsetzung des Protokolls, die ADR 0018 verworfen hat.
2. **Über stdio bei der Ära 2025 bleiben:** ein von Hand verbundener Transport mit einer Instanz pro Verbindung, ohne `serveStdio`. Dann spräche Ecclium über stdio nicht die Version 2026-07-28, die ADR 0018 festlegt.
3. **`serveStdio` mit einer Instanz pro Verbindung, die keine Daten einer Anfrage hält,** und über HTTP eine Instanz pro Anfrage.

## Entscheid

Gewählt ist die dritte Option. Dieses ADR löst ADR 0018 ab. Es übernimmt dessen Entscheid und Konsequenzen mit diesen Abweichungen: Über stdio entsteht eine Instanz pro Verbindung statt pro Anfrage, und «ohne Zustand» heisst ohne Daten einer Anfrage (ADR 0051). Ältere Clients bedient über stdio eine Instanz, die an ihr `initialize` gebunden ist, und über HTTP ist wieder offen, ob sie ohne Sitzung bedient oder abgewiesen werden. Das Serverpaket kommt erst in `core` oder `server`, wenn sein gebündelter Code keine bekannte Schwachstelle hat oder ein eigenes ADR das begründet. Dazu kommt, was die Prüfung des SDK zeigt.

**Weiter gilt aus ADR 0018:**

- Ecclium spricht MCP in der Version 2026-07-28 über `@modelcontextprotocol/server`, im Betrieb über HTTP ab Phase 7 zusammen mit `@modelcontextprotocol/hono`. Über HTTP gehen Antworten im JSON-Modus (`responseMode: 'json'`). Benachrichtigungen während eines Aufrufs, etwa zum Fortschritt, verwirft das SDK in diesem Modus. `subscriptions/listen` beantwortet `createMcpHandler` unabhängig davon immer über SSE, und weil `McpServer` in der Voreinstellung `listChanged` deklariert, bleibt ein solcher Strom offen. Ob Ecclium `subscriptions/listen` abweist, `listChanged` abschaltet oder die Ströme zulässt, ist offen für Phase 7.
- Rückfragen laufen über Multi Round-Trip Requests (`input_required`). Sampling wird nicht benutzt. Alles Zeitgesteuerte läuft im Runner als eigener Prozess.
- **Versionen:** Gepinnt wird die jüngste Version des Serverpakets, die das Mindestalter für neue Versionen erfüllt (ADR 0050). Der Adapter für HTTP kommt mit Phase 7, in einer Version, die zum gepinnten Server passt. Ab dann werden Server und Adapter nur gemeinsam aktualisiert, und das Serverpaket bringt sein Kernpaket `@modelcontextprotocol/core` in genau passender Version mit.
- **stdout im Betrieb über stdio** gehört dem Protokoll, und nur der stdio-Transport des SDK schreibt dorthin. Die Orte im Code stehen in `tests/architecture/boundaries.json`. Der Betrieb über stdio beginnt in `packages/server/src/stdio/` und in `packages/cli/src/stdio/`, und nichts, was von dort aus erreichbar ist, darf auf stdout schreiben. Auf stdout schreiben nur die Meldungen der Kommandozeile in `packages/cli/src/output/`, auf stderr nur der Logger in `packages/core/src/logger/` und dieselben Meldungen. `console` benutzt der Code der Pakete nirgends, `process` nur über einzelne Eigenschaften.
- Das Audit schreibt im Betrieb über stdio über den Logger nach stderr. Im Betrieb über HTTP und im Runner gibt die Kommandozeile dem Audit einen Ausgabestrom mit.
- Die Regel für stdout ist doppelt durchgesetzt, mit dependency-cruiser und ESLint, und ein Test im Betrieb über stdio prüft in Phase 1 zur Laufzeit in einem Kindprozess, dass auf stdout nur Protokollnachrichten erscheinen.
- Was über eine Anfrage hinaus gelten muss, etwa eine offene Bestätigung, liegt nicht im Server, sondern im Kern, mit eigener Frist und eigenem Schutz (ADR 0051).

**Neu:**

- **Einstieg über stdio** ist nur `serveStdio`. Es entsteht eine Instanz pro Verbindung. Die Funktion, die sie erzeugt, ist billig und ohne Nebenwirkung, denn bei einem Client, der zuerst `server/discover` sendet und dann auf `initialize` ausweicht, läuft sie zweimal. Die Instanz hält keine Daten einer Anfrage über diese hinaus (ADR 0051), und der Mandantenkontext entsteht für jeden Aufruf eines Tools neu (ADR 0003).
- **Über HTTP** entsteht in Phase 7 mit `createMcpHandler` eine Instanz pro Anfrage. In ADR 0003 steht «für jede Anfrage entsteht eine Server-Instanz». Das heisst ab diesem ADR: über HTTP pro Anfrage, über stdio pro Verbindung, in beiden Fällen ohne Daten einer Anfrage.
- **Ältere Clients über stdio** bedient `serveStdio` mit `legacy: 'serve'` und dem Shim des SDK für `input_required`. Die Läufe des Spikes zu Elicitation stützen das: Der Shim stellt einem älteren Client, der Elicitation deklariert, die Frage als `elicitation/create`, und Claude Code zeigte sie im Modus Legacy als Dialog. Ein älterer Client ohne Elicitation erhält einen Fehler statt einer Frage. Der Chat von Claude Desktop 2.31226.1 verband sich mit der Protokollversion 2025-11-25, mit `legacy: 'reject'` wäre Ecclium dort nicht nutzbar.
- **Ältere Clients über HTTP** sind offen für Phase 7. `createMcpHandler` bedient sie ohne Sitzung, und eine solche Instanz kennt die Capabilities des Clients nicht. Rückfragen über Elicitation gehen dann nicht. Zur Wahl stehen `stateless` und `reject`. Der Entscheid berührt die Bestätigung von Schreibvorgängen in Phase 5.
- **`requestState`:** Beeinflusst er Logik, ist er mit HMAC signiert und befristet, etwa mit dem Codec des SDK. Er ist an Methode, Mandant und Prinzipal gebunden. Über stdio ist sein Schlüssel zufällig und gilt nur für den Prozess, also für die eine Verbindung. Woher der Schlüssel über HTTP kommt, wo mehrere Prozesse die Runden einer Rückfrage bedienen können, ist offen für Phase 7. Weil `bind` die Parameter nicht sieht, trägt er einen Digest der Parameter, den der Handler beim Wiedereinstieg vergleicht. Er bleibt für den Client lesbar und enthält deshalb keine Geheimnisse und keine Personendaten. Was höchstens einmal gelten darf, etwa eine Bestätigung, verbraucht der Kern selbst, nicht der `requestState`.
- **Antworten auf Rückfragen:** Der Server fragt nur nach Capabilities, die der Client deklariert hat, und verlässt sich nicht darauf, dass eine Antwort kommt. Angenommener Inhalt wird in beiden Ären gegen das Schema geprüft, weil der Shim es nicht tut. Nach einer Ablehnung oder einem Abbruch fragt ein Handler nicht von selbst erneut.
- **Gebündelter Code:** Bis Phase 8, in der die SBOM entsteht, ersetzt eine Liste im Abschnitt «Umsetzung» die Prüfung durch Werkzeuge. Ein Test gleicht sie mit dem installierten Paket ab. Bei jeder neuen Version des SDK prüft eine Person die gebündelten Pakete von Hand auf bekannte Schwachstellen und trägt das Ergebnis mit Datum ein. Eine Version, deren gebündelter Code eine bekannte Schwachstelle hat, kommt nicht in `core` oder `server`, ausser ein eigenes ADR begründet, warum der verwundbare Code dort nicht erreichbar ist.
- **Lizenz:** Server und Kernpaket stehen seit 2.3.0 unter Apache-2.0, die gebündelten Pakete unter MIT, BSD-2-Clause und BSD-3-Clause. Alle stehen auf der Liste der Lizenzen zur Laufzeit.

## Konsequenzen

- Wer den Entscheid zum MCP-SDK lesen will, liest dieses ADR. Mit seiner Annahme trägt ADR 0018 den Status «Abgelöst durch ADR 0053». Verweise auf ADR 0018 in angenommenen ADRs, etwa in ADR 0003, ADR 0020 und ADR 0024, meinen dann die Regeln, die dieses ADR übernimmt. Verweise in Code, Regeln und Dokumentation zeigen mit der Annahme auf dieses ADR.
- Eine Instanz lebt so lange wie die Verbindung, über stdio also so lange wie der Prozess, den der Client startet. Sie hält die verhandelte Ära, die registrierten Tools und offene Anfragen, bei älteren Clients auch deren Capabilities aus `initialize`. Das sind keine Daten einer Anfrage. Legt ein Fehler doch solche Daten in der Instanz ab, trägt er sie in spätere Aufrufe derselben Verbindung. Dagegen stehen die Regel aus ADR 0051 und der Test mit zwei Mandanten (ADR 0003).
- Eine angenommene Rückfrage beweist nicht, dass ein Mensch sie gesehen hat. Ein Hook im Client kann ohne Dialog annehmen, und eine deklarierte Capability heisst nicht, dass jemand antworten kann (Threat Model, T8). Wie die Bestätigung von Schreibvorgängen damit umgeht, legt ADR 0029 vor Phase 5 fest.
- Der `requestState` ist signiert, nicht verschlüsselt. Ein Client kann seinen Inhalt lesen, nicht ändern. Über stdio entsteht der Schlüssel bei jedem Start neu, deshalb gilt nach einem Neustart kein `requestState` von vorher.
- Weil es keinen Haken vor dem Handler gibt, erreichen unbekannte Tools und Fehler bei der Prüfung der Eingabe weder das Audit noch den Logger. Ob ein umhüllender Transport oder ein umhüllendes Schema das in Phase 1 schliesst, entscheidet der Bau des Mounts. Sonst bleibt es ein Restrisiko im Threat Model.
- Die Sperre `[arch:mcp-register]` erfasst auch `registerCapabilities`, `removeRequestHandler`, `removeNotificationHandler` und `readCallback`. Wer ein Objekt hält, das `registerTool`, `registerPrompt` oder `registerResource` zurückgibt, kann den Handler mit `update({ callback })`, `remove()`, `disable()` oder `enabled` und über die Felder `handler` und `executor` austauschen oder abschalten. Diese Namen sind zu allgemein für eine Regel, die Methoden an ihrem Namen erkennt. Der Mount gibt diese Objekte deshalb nicht heraus, und das prüft das Review.
- Restrisiko `fast-uri`: In 2.3.1 bündelt das SDK `fast-uri` 3.1.0. ajv nutzt es für `$id` und `$ref`, wenn es ein JSON-Schema übersetzt. Das SDK übersetzt ein Schema mit ajv nur an zwei Stellen: in `fromJsonSchema()`, das ein JSON-Schema als Schema für ein Tool verpackt, und im veralteten `elicitInput` der Ära 2025, das angenommenen Inhalt gegen das `requestedSchema` prüft. Schemas aus zod (ADR 0025) prüft zod, und `inputRequired.elicit` übersetzt nichts und prüft keine Antwort, auch nicht im Shim. Eine neuere Version des SDK gibt es am 11.10.2026 nicht. Deshalb steht das SDK vorerst nur in `testkit`, für den Spike, der weder `fromJsonSchema()` noch `elicitInput` benutzt. In `core` oder `server` kommt es erst mit einer Version, die `fast-uri` ab 3.1.8 bündelt, oder mit einem eigenen ADR nach der Regel unter «Gebündelter Code», das zeigt, dass Ecclium keinen dieser Wege benutzt.
- Die Liste des gebündelten Codes ist eine Ersatzkontrolle. Der Test erkennt nur Code, den das Werkzeug des Builds mit einem Pfad der Form `node_modules/.pnpm/…` markiert. Diese Markierung ist kein Vertrag und kann mit einem anderen Build verschwinden, dann scheitert der Test an einer leeren Liste. Die Lizenzen der gebündelten Pakete erscheinen im Paket nicht als Hinweise Dritter. Das betrifft die Hinweise, die Phase 8 für das Produktpaket erzeugt.
- Sampling bleibt ungenutzt. Das stützen jetzt die Spezifikation und das SDK.

Sie betreffen das Zerlegen und Normalisieren von URIs: Pfade mit kodierten Punkten, verwechselte Hosts, IPv6-Adressen und Ports.
- Der Spike zu Elicitation liegt in `packages/testkit/src/mcp-spike/`, mit benannten Ausnahmen in `tests/architecture/boundaries.json`. Seine Läufe vom 11.10.2026 gegen Claude Code 2.1.296 und Claude Desktop 2.31226.1 stehen in `docs/research/mcp-sdk-und-elicitation.md` (Ergebnisse). Claude Code zeigte die Rückfrage interaktiv in beiden Ären als Dialog, und über den Shim kam jede Aktion unverändert beim Handler an. Im Code-Tab von Claude Desktop lief nur das Annehmen in der Ära 2026, ebenfalls mit Dialog. Der Chat von Claude Desktop 2.31226.1 verband sich mit 2025-11-25 ohne Elicitation und erhielt vom Shim sofort einen Fehler, ohne Frage.
  - Er signiert den `requestState` mit dem Codec des SDK, gültig 600 Sekunden, gebunden an die Methode. Einen Prinzipal gibt es über stdio nicht, an seiner Stelle steht ein Schlüssel pro Prozess. Sein Tool hat keine Argumente, ein Digest der Parameter entfällt deshalb.
  - Die Capabilities älterer Clients liest er nicht über `getClientCapabilities()`, das das SDK als veraltet markiert. Ein beobachtender Transport (`observe.ts`) protokolliert, was der Client sendet, auch bei Anfragen, die das SDK vor dem Handler beantwortet. Ob ein älterer Client Elicitation deklariert hat, prüft dort der Shim.
  - Angenommenen Inhalt prüft er von Hand gegen das Schema seiner Frage und lädt keine Bibliothek für Schemas.
- Die Startmeldungen der Kommandozeile schreiben vor dem Start über stdio aus `packages/cli/src/notices/` nach stderr, nur Texte aus dem Katalog in `packages/cli/src/messages/` und mit `writeSync` (ADR 0055). Beide Ordner stehen im Ort `stdioReachable` in `tests/architecture/boundaries.json`, und die Regel `no-stdout-from-stdio-modules` hält sie von `packages/cli/src/output/` fern. Über `output/` schreibt `ecclium config check` seinen Bericht nach stdout und Fehler beim Aufruf nach stderr, ebenfalls mit `writeSync`.
- Der Mount in `packages/core/src/mcp/mount.ts` steht seit dem 18.10.2026. Er registriert kein Tool mit `registerTool`, von dessen Objekten die Konsequenzen noch ausgehen, sondern beantwortet `tools/list` und `tools/call` mit zwei eigenen Handlern über `setRequestHandler`. Der eingebaute Handler des SDK lehnt ein unbekanntes Tool und eine Eingabe, die nicht zum Schema passt, ab, bevor Code von Ecclium läuft (Kontext, «Kein Haken vor dem Handler»). Mit den eigenen Handlern erreichen beide die Pipeline: Ein unbekanntes Tool endet dort mit einer Zeile im Audit, eine abgewiesene Eingabe mit einer Zeile im Audit und einer Logzeile. Damit schliesst der Bau des Mounts die Lücke aus den Konsequenzen für diese beiden Fälle, ohne umhüllenden Transport und ohne umhüllendes Schema. Weil kein Tool registriert ist, entstehen auch die Objekte nicht, die einen Handler austauschen oder abschalten könnten.
  - Je Verbindung baut die Fabrik eine Instanz von `McpServer` ohne Capabilities und mit dem werfenden Validator aus ADR 0059. Sie meldet die Capability `tools` mit `listChanged: false`, bevor sie die Handler setzt, weil das SDK beim Setzen die Capability prüft, und setzt `onerror`, das nur das feste Ereignis `mcp_server_error` schreibt, nie die Nachricht. Liste, Schemas und Annotationen baut `createMcpMount` einmal beim Start und friert sie ein, die Fabrik bleibt so billig und ohne Nebenwirkung. `serverInfo` nennt den festen Namen `ecclium-mcp-churchtools` und die Version, die die Wurzel der Komposition übergibt, seit dem 19.10.2026 aus `packages/cli/src/version.ts` (ADR 0057).
  - Ein Aufruf fragt den `TenantResolver` mit der Identität des Starts, nimmt fehlende `arguments` als leere Eingabe, wie die Tools, die das SDK selbst registriert, und gibt der Pipeline das Signal der Anfrage. Der Handler wirft nie, weil das SDK die Nachricht eines Fehlers unverändert an den Client sendet. Schemas, Annotationen und die Form der Antwort beschreibt ADR 0024 (Umsetzung).
  - Vor dem Handler lehnt das SDK weiter ab, ohne Zeile im Audit und ohne Logzeile: eine Anfrage `tools/call` in falscher Form, etwa mit einem Array als `arguments` oder einem `name`, der kein String ist, einen `requestState`, der kein String ist, und in der Ära 2026 einen fehlenden oder falschen Umschlag `_meta`. Keiner dieser Fälle führt ein Tool aus. Das Threat Model führt sie als Restrisiko. Ein Ergebnis prüft das SDK danach nur auf seine Form, nicht gegen das gemeldete Schema der Ausgabe. Dass ein Ergebnis dazu passt, prüft der Test mit Ajv aus ADR 0059.
  - `requestState.verify` ist nicht eingestellt, weil noch kein Handler eine Rückfrage stellt. Einen `requestState`, den ein Client sendet, reicht das SDK deshalb ungeprüft weiter, und der Handler liest ihn nicht. Der erste Handler mit einer Rückfrage stellt die Prüfung nach den Regeln unter «`requestState`» ein.
- Der Server über stdio liegt seit dem 18.10.2026 in `packages/server/src/stdio/`, erreichbar über den Unterpfad `./stdio` von `server`. `startStdioServer` baut den Mount aus dem, was die Wurzel der Komposition übergibt, und bedient ihn mit `serveStdio` und `legacy: 'serve'`. Den Transport baut er selbst, mit einer Grenze von 1 MiB statt der 10 MiB des SDK. Sie gilt nicht je Nachricht, sondern für die Eingabe, die der Transport ungelesen hält: Bevor das SDK Zeilen trennt, prüft es den Rest einer unfertigen Nachricht zusammen mit dem eben gelesenen Stück. Über eine Pipe ist ein Stück höchstens 64 KiB gross, eine Nachricht bis 1 MiB weniger 64 KiB kommt also immer durch. Geht die ungelesene Eingabe über 1 MiB, endet die Verbindung, bevor etwas sie zerlegt, und jede Nachricht darin geht ohne Antwort und ohne Zeile im Audit verloren. Das kann auch eine Nachricht knapp unter 1 MiB treffen, auf die der Client direkt eine weitere folgen lässt. Tests halten fest, dass dieselben zwei Nachrichten von je 600'000 Bytes in eigenen Stücken beide eine Antwort bekommen und in einem Stück die Verbindung beenden. Die Pipeline begrenzt Tiefe und Zahl der Werte einer Eingabe, nicht ihre Grösse. Die Grenze von 1 MiB ist deshalb die einzige Grenze für die Grösse vor dem Schema des Tools. Eine Grenze für die Tiefe beim Zerlegen gibt es nicht, die Pipeline prüft die Tiefe erst danach. Ein Fehler der Verbindung schreibt nur das feste Ereignis `mcp_stdio_error`, nie seine Nachricht, denn das SDK setzt Teile der Nachricht des Clients hinein. Ohne eigene Ströme liest der Transport stdin und schreibt stdout des Prozesses, Tests geben ihm eigene Ströme. Der Einstieg gibt nur eigene Funktionen und Typen heraus, nie den Mount, seine Fabrik oder ein Objekt des SDK, das prüft der Test der Exportfläche. Signale und das Ende des Prozesses regelt die Wurzel der Komposition. Seit dem 19.10.2026 gibt `startStdioServer` dafür neben `close` das Versprechen `closed` heraus. Es erfüllt sich, sobald die Verbindung endet, auf welchem Weg auch immer: Ende oder Schliessen der Eingabe, ein Fehler der Ausgabe, ungelesene Eingabe über der Grenze oder `close`, auch wenn das Schliessen scheitert. Es lehnt nie ab. `serveStdio` nimmt `onclose` des Transports für sich, deshalb baut der Server den Transport aus einer Unterklasse des Transports des SDK, die `close` überschreibt, durch das jeder dieser Wege läuft, und fasst keinen Callback des SDK an.
- Der Test im Betrieb über stdio, `tests/mcp-stdio.test.mts`, startet seit dem 18.10.2026 `tests/fixtures/stdio/server.mts` als Kindprozess. Das Fixture baut den Server über stdio aus dem Quelltext wie eine Wurzel der Komposition: Konfiguration im Code, das Beispiel-Plugin aus `testkit`, das Testdouble statt ChurchTools, der Modus `interactive` und Zeilenschreiber, Logger und Audit des Kerns auf dem echten fd 2. Den Mount erreicht es nur über `packages/server/src/stdio/`, das prüft ein Test an seinem Quelltext. Ein Haken für die Auflösung, `tests/fixtures/stdio/hooks.mts`, bildet die Importe der Pakete auf `.js` auf ihre Quellen ab. Der Test startet das Kind mit `--conditions=@ecclium/source` und einer eigenen Umgebung, die nur die Netzsperre über `NODE_OPTIONS` und das Token als Kanarienwert enthält. Er spielt in beiden Ären eine ganze Sitzung durch, nach `server/discover` oder nach `initialize`, mit `tools/list` und `tools/call`, auch nach einem unbekannten Tool, einer abgewiesenen Eingabe, einer Zeile, die kein JSON ist, einem Fehler des Testdoubles und einem abgebrochenen Aufruf. Auf stdout steht Zeile für Zeile nur JSON-RPC 2.0, und das Token erscheint weder auf stdout noch auf stderr. Die ganze Zeile eines Ergebnisses genau an der Grenze der Pipeline ist in der Ära 2026 64'730 Bytes lang und in der Ära 2025 64'606, also unter 64 KiB. Gegenproben über Schalter des Fixtures: Eine eigene Zeile auf stdout macht die Prüfung rot, und ein Versuch nach aussen scheitert an der Netzsperre. Geprüft ist damit der Server über stdio in einem Fixture. Den Prozess der Kommandozeile prüft seit dem 19.10.2026 ein eigener Test (siehe unten).
- Audit-Datei über stdio, seit dem 23.10.2026: Mit `ECCLIUM_STATE_DIR` schreibt die Senke jede Zeile des Audits zuerst in die Audit-Datei und erst danach über den Logger nach stderr. Der Entscheid, dass das Audit über stdio nach stderr geht, bleibt damit wahr, die Zeile dort ist dann eine Kopie (ADR 0028).
- Der Start über stdio in `packages/cli/src/stdio/` steht seit dem 19.10.2026, als Unterbefehl `ecclium stdio` des einen Befehls (ADR 0055). Er schreibt die Startmeldungen, bevor Server, SDK und undici laden, baut dann den einen Zeilenschreiber, Logger, Senke des Audits, Transport, Pipeline und den Server mit dem Modus `interactive` und lässt den Prozess enden, wenn `closed` sich erfüllt (ADR 0054, ADR 0055). `tests/stdio-start.test.mts` startet `ecclium stdio` aus dem Quelltext als Kindprozess, wie ein Client ihn startet, mit der Netzsperre und einer gefilterten Umgebung. In beiden Ären steht auf stdout Zeile für Zeile nur JSON-RPC 2.0, `tools/list` nennt genau `ct_whoami`, und auf stderr stehen zuerst die Startmeldungen, danach nur JSON. Der Adapter für HTTP folgt in Phase 7.
- Prompts, seit dem 26.10.2026: Der Mount meldet die Fähigkeit `prompts` mit `listChanged: false` und beantwortet `prompts/list` und `prompts/get` mit eigenen Handlern, nicht mit `registerPrompt`. Eine Ablehnung wirft er als `ProtocolError` mit festem Satz, weil das SDK die Nachricht eines Fehlers unverändert an den Client schickt ([ADR 0065](0065-mcp-prompts-als-feste-vorlagen.md)).
