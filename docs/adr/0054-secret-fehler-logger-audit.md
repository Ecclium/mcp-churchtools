# ADR 0054: Secret, Fehler mit stabilem Code, Logger und Audit als JSON Lines

- Status: Vorgeschlagen
- Datum: 14.10.2026
- Fällt vor: Phase 1

## Kontext

Ein Login-Token von ChurchTools trägt alle Rechte seines Kontos (Threat Model, T4). Personendaten dürfen weder das Protokoll noch eine Fehlermeldung erreichen (T5). ADR 0053 legt fest, dass im Betrieb über stdio nach den Startmeldungen der Kommandozeile (ADR 0055) nur der Logger auf stderr schreibt und dass das Audit über denselben Weg geht. ADR 0024 führt jeden Aufruf eines Tools durch eine Pipeline, die Fehler in einen Code übersetzt. Vor der Pipeline braucht der Kern deshalb vier Bausteine: einen Typ für Geheimnisse, einen Fehler mit stabilem Code, einen Logger und eine Senke für das Audit. Alle vier nehmen Werte von Code an, dem sie nicht trauen: von Plugins, von Tools und, über deren Fehler, von ChurchTools.

Geprüft an Node.js 24.21.0, zod 4.6.5 und TypeScript 6.0.3. Die Tests der Bausteine zeigen jeden Befund, soweit er nicht nur eine Messung ist:

- **Ausgabe von Node.js selbst:** Der Drucker für einen nicht gefangenen Fehler, ein nicht behandeltes Ereignis `error` und `console.dir` mit `customInspect: false` umgehen eine eigene Methode für `util.inspect`. Einen Wert hält dort nur ein privates Feld zurück (`tests/secret-output.test.mts`).
- **Reguläre Ausdrücke:** Nach einem Treffer halten die alten statischen Eigenschaften wie `RegExp.$_` die ganze Eingabe, lesbar für jedes Modul im Prozess. Ein Ausdruck mit dem Flag `g` oder `y` behält zwischen zwei Aufrufen seinen `lastIndex`.
- **Mehrere Kopien eines Pakets:** `instanceof` erkennt einen Fehler aus einer zweiten Kopie von `plugin-api` nicht. `Symbol.for` liefert dagegen in jeder Kopie und in jedem Realm dasselbe Symbol.
- **zod:** `safeParse` ruft Getter und Fallen eines Proxys auf und lässt den Fehler eines Getters durch. `z.strictObject` liest geerbte Schlüssel. `z.array().max()` prüft jeden Eintrag, bevor die Grenze greift. Bei einem Objekt liest zod Eigenschaften wie `length` auch dann, wenn die Prüfung des Typs schon gescheitert ist. Eine Fehlerkarte erhält den geprüften Wert, und die Meldungen können Namen unbekannter Schlüssel enthalten. Die Option `abort: true` an `.max()` beendet die Prüfung eines zu langen Strings vor seinem Muster.
- **Proxys:** `isProxy` aus `node:util/types`, dieselbe Funktion wie `util.types.isProxy`, erkennt einen Proxy, auch einen widerrufenen und einen aus einem anderen Realm, ohne eine Falle aufzurufen.
- **Schreiben auf fd 2:** `writeSync` mit einer Position, auch 0, scheitert auf einer Pipe mit ESPIPE und überschreibt bei einer Datei deren Anfang (`tests/logger-output.test.mts`). Sobald etwas `process.stderr` berührt, auch eine Warnung von Node.js oder das SDK, wird fd 2 nicht blockierend, und wer `process.stdout` berührt, macht ebenso fd 1 nicht blockierend. Dann gibt es EAGAIN und Teilschreibvorgänge. Eine blockierende Pipe, die niemand leert, hält `writeSync` an, bis der Leser liest. Laut einer Probe mit Node.js 24.15, 24.21 und 26.10 unter macOS genügt schon das Laden eines Moduls: `node:util` als ES-Modul macht fd 2 nicht blockierend, gleich welchen Export ein Modul nimmt, auch als `util` ohne Präfix und als `node:sys`. `node:process` als ES-Modul macht fd 0, fd 1 und fd 2 nicht blockierend, auch mit einem einzelnen benannten Import wie `exitCode`. `node:util/types` und die Eigenschaften `argv`, `env`, `exitCode` und `platform` des globalen `process` lassen alle drei blockierend. Fd 2 machen ausserdem `node:assert`, `node:http`, `node:http2`, `node:repl` und `node:test` nicht blockierend, `node:test` auch fd 1, dazu jedes Modul, das beim Laden eine Warnung ausgibt, veraltet wie `node:punycode` oder experimentell wie `node:wasi` und unter Node.js 26 `node:ffi`. Die Warnung schreibt erst nach dem Laden auf `process.stderr`. Das Serverpaket des MCP-SDK lädt in Version 2.3.1 `node:process` in seinem Shim für Node.js, den seine Einstiege für den Server und für stdio laden, und der Netzwächter der Tests lädt es ebenfalls (ADR 0052). `tests/blocking-descriptors.test.mts` prüft in CI unter Linux, dass `node:util`, `node:process` und ein Modul mit einer Warnung beim Laden fd 2 nicht blockierend machen und dass `node:util/types` und die Module der Pakete, die der Test aus den Quellen laden kann, es blockierend lassen. Wird dort ein Fall zu `node:util` oder `node:process` rot, etwa nach einem Update von Node.js, sind diese Angaben veraltet und werden nachgeführt. `process.stderr._handle.setBlocking(true)` macht fd 2 wieder blockierend, auch gegen Module, die danach laden. Das ist nur unter macOS beobachtet und nicht getestet. Die Schnittstelle ist nicht dokumentiert, und eine Datei als stderr hat kein `_handle`, blockiert aber ohnehin.
- **JSON:** `JSON.stringify` lässt U+2028 und U+2029 unmaskiert. Eine Funktion `toJSON` auf `Object.prototype` ändert die Ausgabe gewöhnlicher Objekte und Arrays, nicht aber die eines Objekts ohne Prototyp.

## Optionen

1. **Secret:** ein Objekt mit eigener Methode für `util.inspect`, oder ein privates Feld mit `toString`, `toJSON` und `util.inspect`, die alle einen Platzhalter liefern. Nur das private Feld hält den Wert auch aus den Ausgaben von Node.js selbst heraus.
2. **Fehler erkennen:** mit `instanceof`, am Feld `code` allein, oder an einer Marke mit `Symbol.for`. `instanceof` scheitert an einer zweiten Kopie, `code` allein trifft jeden fremden Fehler von Node.js.
3. **Fremde Werte prüfen:** mit zod, oder durch eigenes Lesen eigener Dateneigenschaften. zod führt Code des Werts aus und gibt den Wert an Fehlerkarten weiter.
4. **Schreiben:** mit `process.stderr.write`, das asynchron werden kann und Zeilen puffert, oder mit `writeSync` auf fd 2, mit oder ohne Warten bei EAGAIN.
5. **Ungültiges Audit-Ereignis:** werfen, verwerfen, oder mit Ersatzwerten schreiben und melden.

## Entscheid

Gewählt sind jeweils das private Feld, die Marke, das eigene Lesen, `writeSync` ohne Warten und das Schreiben mit Ersatzwerten. Im Einzelnen:

### Secret

- `Secret` in `packages/core/src/http/secret.ts` hält seinen Wert in einem privaten Feld. `toString`, `toJSON` und `util.inspect` liefern `[REDACTED]`. Die Klasse ist final, Instanz, Prototyp und Klasse sind eingefroren.
- Ein Secret nimmt 1 bis 4096 sichtbare ASCII-Zeichen ohne Leerzeichen an und keinen Wert, der `REDACTED` enthält. Geprüft wird Zeichen für Zeichen, nicht mit einem regulären Ausdruck. Die Meldung eines abgelehnten Werts nennt den Wert nie.
- Den Wert liest nur `revealSecret`. Das Modul exportiert die Funktion, der Einstieg `http/index.ts` nicht, und die Regel `egress-internals` von dependency-cruiser erlaubt den Import in den Paketen nur aus `packages/core/src/http/`, dem ausgehenden Weg (ADR 0022). `tests/` und `scripts/` prüft dependency-cruiser nicht. Dort verlangt ein Test, dass keine Datei mit Code den Namen `revealSecret` nennt.

### Fehler

- `EccliumError` in `plugin-api` trägt einen Code aus der festen Liste `errorCodes`, eine Nachricht und für den Code `permission` die fehlenden Rechte. Code, Nachricht und die Marke `Symbol.for('ecclium.mcp-churchtools.error.v1')` sind eigene Eigenschaften, die sich nicht ändern lassen, die fehlenden Rechte ebenso, wo der Konstruktor sie setzt. Die Marke ist nicht aufzählbar. Einen `cause` gibt es nie, weil er fremden Text trägt.
- Der Konstruktor wirft nie, auch nicht für Aufrufer ohne Typen. Ein unbekannter Code wird `internal` mit leerer Nachricht. Die fehlenden Rechte werden ohne Getter und ohne Iterator kopiert: erst die Länge, 1 bis 32, dann jeder Eintrag über seinen Index, jeder Name druckbares ASCII mit 1 bis 100 Zeichen ohne Leerzeichen am Rand. Ein schlechter Eintrag verwirft die ganze Liste. Eine Unterklasse darf `name` setzen, ein Feld `code` oder `message` lässt ihren Konstruktor werfen. Rechte, die eine Unterklasse selbst setzt, sind nicht gesperrt, der Kern prüft sie wie jedes andere Feld.
- `isEccliumError` prüft Marke, bekannten Code und Nachricht als eigene Dateneigenschaften und wirft nie. Die Fallen eines Proxys laufen dabei. Der Kern entscheidet deshalb nur über `describeError`.
- `describeError` in `packages/core/src/errors/` macht aus jedem geworfenen Wert ein eingefrorenes `{ code, message, missingRights? }`. Es weist einen Proxy ab, bevor es etwas liest, und liest jedes Feld einmal als eigene Dateneigenschaft. Die Nachricht eines `EccliumError` bleibt, wenn sie eine Zeile druckbares ASCII mit 1 bis 500 Zeichen und nicht leer ist, sonst steht der feste Satz des Codes. Der Code `internal` gibt immer seinen festen Satz. Jeder andere Wert wird `internal`: Nachricht, Stack, Ursache, Name und Code eines fremden Fehlers gehen nie weiter, und kein fremder Code wird hier übersetzt. Die Tabelle der festen Sätze ist eingefroren und hat keinen Prototyp.
- **Nur ASCII:** Nachrichten und Namen von Rechten sind auf druckbares ASCII beschränkt, enger als «druckbar». So kommen weder Zeilenumbrüche noch Steuerzeichen noch unsichtbare Zeichen wie U+FE0F zum Modell. Eine Nachricht mit Umlaut erhält deshalb den festen Satz.
- **Die Marke wählt aus, sie beweist nichts.** Jeder Code im Prozess kann sie setzen. Er gewinnt damit nichts, was ein echter `EccliumError` mit demselben Inhalt nicht auch gäbe, darum prüft der Kern jedes Feld neu.
- **Neue Codes:** Zur Laufzeit wird ein Code, den der Kern nicht kennt, `internal`. Im Typ bricht ein neuer Code erschöpfende Tabellen über `ErrorCode` und die Zuweisung eines Fehlers aus einer neueren Kopie an eine ältere. Solange `plugin-api` unter 1.0 steht, kommt ein neuer Code mit einer Minor-Version, ab 1.0 mit einer Major-Version. Der Kern muss einen Code kennen, bevor ein Plugin ihn benutzt.

### Logger

- Eine Zeile trägt `ts`, `level` und `event`, dann `tenantId`, `runId`, `eventId`, `tool`, `code`, `mode`, `redaction`, `readOnly`, `durationMs`, `count`, `status` und `attempt` in dieser Reihenfolge, dann `dropped`. Es gibt kein Feld für Nachrichten, Namen, Pfade, Hosts, URLs oder anderen Text, und weder `v` noch `type`, damit keine Logzeile als Audit-Zeile gilt. Jeder Wert hat ein Muster, eine geschlossene Liste oder einen Bereich ganzer Zahlen und wird nie umgewandelt. Die längste mögliche Zeile hat 544 Zeichen.
- **Wer was setzt:** `tenantId`, `runId`, `eventId`, `tool`, `mode`, `redaction` und `readOnly` bindet nur der Kern an einen Logger. Ein Aufruf setzt nur `code`, `durationMs`, `count`, `status` und `attempt`. So schreibt kein Tool Zeilen im Namen eines anderen Mandanten, Laufs oder Tools. Jeder andere Name, ein ungültiger Wert, ein Getter und eine nicht aufzählbare Eigenschaft fallen weg und werden in `dropped` gezählt, höchstens bis 1 000 000. Ein Ereignisname, der sein Muster `^[a-z][a-z0-9_]{0,63}$` bricht, wird `invalid_event`.
- Felder werden als eigene Dateneigenschaften eines einfachen Objekts gelesen. Ein Proxy, eine Klasseninstanz, eine Map oder ein Fehler wird als Ganzes abgewiesen. Die Zeile entsteht auf einem Objekt ohne Prototyp.
- Die Zeit kommt nur aus der übergebenen Uhr. Darum nimmt `createLogger` eine Uhr an, anders als die geplante Signatur `createLogger({ writer, minLevel, bound })`. Scheitert die Uhr, steht `1970-01-01T00:00:00.000Z`, nicht die Zeit des Systems. `systemClock` in `packages/core/src/clock.ts` ist die eingefrorene Uhr des Systems.
- Ein Logger ist eingefroren, seine Methoden funktionieren losgelöst, geben nichts zurück und werfen nie. Ein Aufruf aus der eigenen Uhr oder dem eigenen Schreiber, während er schreibt, fällt weg.
- **Zeilenschreiber:** `createStderrWriter` schreibt jede Zeile mit einem `writeSync` auf fd 2, mit genau vier Argumenten und dem Zeilenumbruch im selben Aufruf. Einen Teilschreibvorgang setzt er am Versatz fort. Nach vier Aufrufen ohne die ganze Zeile gilt sie als verloren, und die nächste Zeile beginnt mit einem Zeilenumbruch. EAGAIN versucht er sofort erneut, ohne zu warten: Ein Leser, der stderr nicht leert, kostet Zeilen, keine Zeit. EPIPE und EBADF schliessen den Schreiber endgültig. Er nimmt nur Zeilen aus druckbarem ASCII mit höchstens 65 536 Zeichen, meldet mit seinem Rückgabewert, ob die ganze Zeile geschrieben ist, und zählt Verluste in einem eingefrorenen Abbild. Er wirft nie und schreibt nichts über einen Fehler. Er berührt `process.stderr` nicht, und nichts in `packages/core/src/logger/` schliesst eine Datei. Ein Test prüft die Quellen des Ordners darauf.

### Audit

- `auditEventV1Schema` in `packages/core/src/audit/schema.ts` beschreibt ein Ereignis der Version 1 mit zod und ist die Quelle für das spätere JSON Schema (ADR 0028). Es ist strikt, jedes Feld hat ein Muster oder eine geschlossene Liste, `objectRefs` hat höchstens 100 und `pluginHashes` höchstens 64 Einträge, und ein Fehlercode steht genau dann, wenn das Ergebnis `error` oder `denied` ist. Ein Typtest prüft, dass Ein- und Ausgabe des Schemas `AuditEventV1` gleichen.
- **Was die Muster ausschliessen:** Die Muster halten E-Mail-Adressen, Leerzeichen, Zeilenumbrüche und anderen freien Text fern. Eine `actor.id` ist eine neutrale Bezeichnung wie `stdio:local-stdio`, ohne Grossbuchstaben, Punkt, `@` und Leerzeichen. Ein Eintrag in `objectRefs` nennt eine Art aus einer geschlossenen Liste, vorerst `person`, `group`, `wiki_category` und `wiki_page`, und eine ID, eine Zahl oder eine UUID, etwa `person:1`. `dataProtectionRegime` und `provider.transferBasis` sind Begriffe wie `eu_gdpr`, nie Text mit Leerzeichen oder Punkt. Welche Begriffe es gibt, ist offen, bis dahin passt jeder Begriff dieser Form. `provider.model` enthält keinen Schrägstrich, `provider.endpointHost` ist ein Hostname in Kleinbuchstaben ohne Port, Benutzer oder Pfad. Ein Name in der Form eines Slugs wie `max-mustermann` passt dagegen auf die IDs von Mandant, Routine und Akteur. Diese kommen deshalb nur aus der Konfiguration und der Identität.
- `createAuditSink({ writer, clock, isKnownTool, newId? })` schreibt pro Aufruf eine Zeile über den Zeilenschreiber des Loggers. Anders als die geplante Signatur `{ writer, clock }` braucht die Senke die Prüfung der Registry, weil ein Muster `ct_max_mustermann` nicht von einem echten Tool unterscheidet, und eine austauschbare Quelle für IDs, damit Tests ganze Zeilen prüfen. Ein Tool, das die Registry nicht kennt, steht als `ct_unknown`.
- Die Senke setzt `v`, `eventId` aus `randomUUID` und `ts` aus der Uhr. Mitgegebene Werte dafür und für `seq` und `prevHash` fallen weg und werden gemeldet. Sie liest nur eigene Dateneigenschaften. Ein Getter gilt als ungültig und läuft nie, ein Proxy oder ein Wert, der kein Objekt ist, ergibt eine Zeile aus Ersatzwerten. Listen kopiert sie über den Index, nachdem sie die Länge geprüft hat. Kopien und Zeile haben keinen Prototyp, und das JSON entsteht von Hand aus geprüften einfachen Werten. zod fragt sie nur, ob ein Wert passt, nie nach dem Fehler, und ein Wert des Entwurfs geht nur als einfacher Wert an zod, nie als Objekt.
- **Ersatzwerte:** Ein ungültiges Pflichtfeld erhält einen Ersatzwert: Mandant `invalid`, Akteur `{ kind: 'service', id: 'invalid' }` als Ganzes, Modus `unattended`, Ergebnis `error`, Fehlercode `internal`, keine `objectRefs`, Dauer 0. Scheitern die Quelle der IDs oder die Uhr, stehen `00000000-0000-0000-0000-000000000000` und `1970-01-01T00:00:00.000Z`. Ein ungültiges optionales Feld fällt weg. Der Akteur wird ganz ersetzt, damit eine gültige ID nie unter einer falschen Art steht. Die Konfiguration muss Mandant und Akteur `invalid` abweisen, die Registry das Tool `ct_unknown`.
- **Meldungen:** Jedes ungültige Feld ergibt eine Logzeile mit einem festen Ereignis wie `audit_invalid_tenant_id`, dem Code `validation` und der ID des Ereignisses, nach der Audit-Zeile. Weitere feste Ereignisse sind `audit_invalid_event_id`, `audit_invalid_ts`, `audit_missing_error_code`, `audit_reserved_<feld>`, `audit_unknown_fields` mit der Anzahl, `audit_unreadable` und `audit_schema_mismatch`, dieses mit dem Code `internal`. Die Logzeile nennt den Mandanten nur, wenn er gültig war. Unbekannte Schlüssel werden gezählt, nie genannt. Eine Zeile mit den Namen der Felder gibt es nicht, weil die freigegebenen Felder der Logzeile keinen Text tragen.
- Zum Schluss prüft das Schema die ganze Zeile. Passt sie nicht, hat die Senke einen Fehler, und die Zeile enthält nur Ersatzwerte.
- `record` wirft nie und gibt nichts zurück. Eine Zeile, die der Schreiber nicht ganz schreiben konnte, zählt `failures()` und fällt weg. In Phase 1 liest der Server nur. Ab den schreibenden Tools sperrt ein gescheitertes Audit das Schreiben, das regelt ein späteres ADR.

### Aufgaben der Wurzel der Komposition

- Sie erzeugt den Zeilenschreiber einmal und gibt ihn an Logger und Audit. Der Einstieg von `core` exportiert den Schreiber nicht, sonst schrieben Tools beliebigen Text nach stderr. Die Wurzel erreicht ihn nur über den Unterpfad `./composition` von `core`, zusammen mit Logger, Senke des Audits, Uhr, `describeError` und einem Logger, der an den Mandanten `default` gebunden ist. Diesen Unterpfad darf nur die Wurzel der Komposition importieren, das hält eine Regel. Erwogen war eine Fabrik im Kern, die Schreiber, Logger und Audit baut und den Schreiber nie herausgibt. Sie bräuchte trotzdem einen Weg für den Schreiber in die Pipeline und Nähte für Tests.
- Sie installiert Handler für `uncaughtException` und `unhandledRejection`, gleich nach dem Logger, die nur `describeError(error).code` über den Logger schreiben, mit `internal`, falls das scheitert, und danach den Prozess mit 70 beenden, weil sein Zustand unbekannt ist. Ohne sie druckt Node.js Nachricht und Stack eines Fehlers nach stderr.
- Im Betrieb über stdio setzt sie fd 2 in Phase 1 nicht zurück, auch wenn das MCP-SDK und undici es beim Laden nicht blockierend machen. Die Startmeldungen schreibt eine erste Stufe, bevor SDK und undici laden, also noch blockierend. Beim Ende schreibt sie das feste Ereignis `stdio_closed` mit der Zahl der verlorenen Zeilen. Vor den Suchtools wird das neu entschieden, nach einer Messung unter macOS und Linux, weil deren Aufrufe Personendaten der besonderen Kategorie betreffen (Konsequenzen, «Verlust und Stillstand beim Schreiben»).
- Der äusserste Fang der Pipeline antwortet `internal`, ohne etwas aufzurufen, falls `describeError` bei erschöpftem Stack selbst mit einem RangeError scheitert.

## Konsequenzen

- **Ereignisname als Kanal:** Ein Ereignisname nimmt bis zu 64 Zeichen aus Kleinbuchstaben, Ziffern und Unterstrich auf. Ein Geheimnis dieser Form käme unverändert ins Log. Ereignisnamen müssen deshalb Konstanten sein. Kleinere Kanäle sind `dropped`, dessen Wert ein Aufrufer über die Zahl der Felder wählt, und die Felder mit ganzen Zahlen.
- **Nachricht eines Tools:** Eine gültige Nachricht aus ASCII kann ein Token, einen Namen oder fremden Text enthalten. Seit dem 18.10.2026 maskiert die Pipeline darin, was die Form einer E-Mail-Adresse, einer Telefonnummer oder eines Datums hat (ADR 0024). Ein Token, einen Namen oder anderen fremden Text erkennt diese Maske nicht, sie gehen so zum Modell, bis die vollständige Maskierung sie erreicht (ADR 0026). Tools setzen keine Inhalte des Mandanten und keinen Text fremder Fehler in eine Nachricht. Log und Audit tragen nur den Code.
- **Verlust und Stillstand beim Schreiben:** Eine blockierende Pipe, die der Client nicht leert, hält den ganzen Server an. Ist fd 2 nicht blockierend, gehen Log- und Audit-Zeilen verloren, sobald mehr anfällt, als der Puffer der Pipe fasst, gezählt in `stats().failed` und `failures()`. Kein eigener Import im ausgelieferten Code der Pakete lädt ein Modul, das fd 2 nicht blockierend macht, ausser `node:util` für `parseArgs` im Befehl der Kommandozeile, den der Start über stdio nie lädt. Das MCP-SDK lädt `node:process` in Version 2.3.1 aber selbst, und undici lädt `node:assert` (ADR 0056). Im Betrieb über stdio ist fd 2 deshalb nicht blockierend, sobald Server und Transport geladen sind. In Phase 1 bleibt das so: Ein Client, der stderr nicht leert, kostet Zeilen, keine Zeit, und die Antworten auf stdout erreichen ihn weiter. Beim Ende nennt `stdio_closed` im Feld `count` die Zahl der verlorenen Zeilen. Diese Zeile kann bei einem Client, der stderr nie liest, selbst verloren gehen, dann bleibt keine Spur. Ein Test am echten Prozess hält stderr an: Alle Antworten kommen auf stdout an, und `stdio_closed` zählt danach die verlorenen Zeilen. Verworfen sind für Phase 1 das Zurücksetzen mit `process.stderr._handle.setBlocking(true)`, das eine nicht dokumentierte Schnittstelle nutzt, unter Linux nicht gemessen ist, einen eigenen Ort für stderr bräuchte und einen solchen Client auch die Antworten auf stdout anhalten liesse, und eine eigene Datei für Log und Audit, die eine neue Variable und einen Ort für Daten bräuchte und deren Zeilen der Client nicht mehr sähe. Vor den Suchtools wird das neu entschieden, nach einer Messung unter macOS und Linux. Zeilen von Node.js selbst oder vom SDK können zwischen den eigenen stehen oder eine eigene Zeile teilen, Leser überspringen Zeilen, die kein JSON sind.
- **Ausnahme ohne Fang:** Nach einer nicht gefangenen Ausnahme oder einer nicht behandelten Ablehnung endet der Prozess sofort mit 70. Ein Aufruf, der gerade läuft, verliert dann seine Zeile im Audit, und eine Antwort auf stdout kann abgeschnitten sein. Die eine Zeile mit dem Code kann verloren gehen wie jede andere.
- **IDs der Ereignisse:** Die Logzeilen eines Aufrufs und seine Zeile im Audit tragen verschiedene `eventId`: Die Pipeline bindet eine an den Logger des Kontexts, die Senke setzt eine eigene. Eine Logzeile lässt sich ihrer Zeile im Audit deshalb nur über Mandant, Tool und Zeit zuordnen. Ein eigener Pull Request gleicht die beiden an.
- **Geschlossenes stderr:** Nach EPIPE oder EBADF gehen alle weiteren Log- und Audit-Zeilen des Prozesses verloren. Vor dem Schreiben in eine Datei, die fd 2 nach einem Schliessen übernommen hat, schützt die Regel, dass nichts fd 2 schliesst, nicht der Umgang mit EBADF.
- **Ersatzwerte sind echte Werte:** `unattended`, `error`, `internal` und eine Dauer von 0 kommen auch regulär vor. Ob ein Wert ersetzt wurde, zeigt nur die zugehörige Logzeile, und die ist ein eigener Schreibvorgang, der für sich scheitern kann.
- **Grenzen der Prüfungen:** Code im Prozess, der Objekte von JavaScript selbst verändert, etwa `Object.getOwnPropertyDescriptor` oder `Array.prototype.includes`, hebelt jede Prüfung aus. Code im Prozess gilt als vertrauenswürdig, wie bei der Marke und beim Symbol des Secret. Ein Inspektor, ein Heap-Snapshot oder ein Core-Dump zeigen ein Secret. `structuredClone` entfernt Marke und Code eines Fehlers. Die Schemas von zod auf Modulebene ändern beim ersten Prüfen innere Zwischenspeicher, eine Lücke der Regel aus ADR 0051.
- **Grenzen der Muster:** Ein Name in der Form eines Slugs passt auf die IDs von Mandant, Routine und Akteur, und bis das Vokabular feststeht, passt jeder Begriff der richtigen Form in die rechtlichen Felder. Diese Werte kommen aus Konfiguration und Identität, nicht von Tools. Umgekehrt kann ein Muster einen echten Wert abweisen, etwa eine Modell-ID mit Schrägstrich. Die Prüfung der Konfiguration beim Start nutzt dieselben Muster, damit ein ungültiger Wert dort auffällt und nicht in jedem Ereignis.
